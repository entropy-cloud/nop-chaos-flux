## [P1-1] `user-edit` resubmit silently loses edited text during active streaming

_Justification: silent, unrecoverable data loss of user input on a plausible flow; the engine reentrancy guard (which fixed prior F1.1) drops the call with zero feedback._

- **文件:** `packages/flux-renderers-ai/src/renderers/ai-bubble/user-edit.tsx:54-68` (pencil button never disabled: `user-edit.tsx:95-104`)
- **证据片段:**
  ```tsx
  async function resubmit() {
    const text = draft.trim();
    if (text.length === 0) return;
    const msgs = e.getMessages();
    const idx = msgs.findIndex((m) => m.id === message.id);
    if (idx < 0) {
      cancelEdit();
      return;
    }
    e.setMessages(msgs.slice(0, idx)); // no-op when isProcessing (create-engine.ts:140)
    cancelEdit(); // clears draft + closes editor
    await e.sendMessage(text); // no-op when isProcessing (create-engine.ts:178)
  }
  ```
- **现状:** The pencil edit button on user-message bubbles is never disabled during streaming. `resubmit()` clears local draft state (`cancelEdit()`) _before_ the silently-dropped `sendMessage`, so when a turn is in-flight the edited text is irrecoverably gone with no user feedback.
- **风险:** User edits a previous message while the assistant is streaming → edited text vanishes, conversation unchanged, no error/toast. `ai-sender`'s submit button IS disabled during loading; this path is the inconsistency.
- **建议:** Disable the pencil button when `ctx?.isProcessing` (mirror `ai-sender`'s `disabled={loading}`), or guard `resubmit` with `if (e.getState().isProcessing) return;` and keep the editor open with a message.
- **复核:** Review verdict **保留 P1** (live code confirmed: no disabled prop on pencil button, both engine methods silently no-op). Closest to P0 but kept P1 — trigger needs edit-during-streaming and the engine itself stays stable.

## [P1-2] `useConversation` create/rename storage errors bypass the `onStorageError` callback

_Justification: contract break — 2 of 5 storage phases silently swallow failures, so hosts cannot observe create/rename persistence failures as documented (AI-28)._

- **文件:** `packages/flux-renderers-ai/src/adapters/use-conversation.ts:254` (createConversation) and `:313` (renameConversation)
- **证据片段:**
  ```ts
  // :254 — bare, no reportStorageError, no .catch()
  void storage?.saveConversation?.(info);
  // :313 — same bare pattern
  void storage?.saveConversation?.({ ...updated, title, updatedAt: now });
  // Contrast — every other storage site routes through reportStorageError:
  //   :169/:173 saveMessages, :211 loadConversations, :274 loadMessages, :304 deleteConversation
  ```
- **现状:** The AI-28 `onStorageError` host callback (promised for all phases, incl. `'saveConversation'` in the `ConversationStorageErrorEvent.phase` union at `:38`) is bypassed for conversation creation and renaming. The bare `void …?.()` also produces an unhandled rejection if `saveConversation` returns a rejected promise.
- **风险:** Host cannot toast/retry/log create/rename persistence failures; in-memory list and persisted store silently diverge (conversation exists in memory but not in storage) with no way for the host to detect it.
- **建议:** Wrap both sites with the existing `Promise.resolve(...).catch(error => reportStorageError({ phase: 'saveConversation', conversationId, error }))` pattern already used elsewhere in the file. Mechanical consistency fix.
- **复核:** Review verdict **保留 P1** (both line numbers + `reportStorageError` existence/usage confirmed).

## [P1-3] `switchConversation` stale-closure race corrupts the engine cache on rapid switching

_Justification: real, user-triggerable state-corruption defect (activeId ≠ activeEngine) with no cancellation guard._

- **文件:** `packages/flux-renderers-ai/src/adapters/use-conversation.ts:258-285`
- **证据片段:**
  ```ts
  async function switchConversation(id: string): Promise<void> {
    setActiveId(id); // (A) immediate
    let engine = engineCache.get(id);
    if (!engine) {
      engine = buildEngineFor(id);
      engineCache.set(id, engine);
      if (storage) {
        /* await */ const stored = await storage.loadMessages(id); /* … */
      }
    }
    setActiveEngine(engine); // (C) runs AFTER await — closure `engine`
    for (const [cachedId, cachedEngine] of engineCache.entries()) {
      if (cachedId === id) continue; // closure `id`, NOT current activeId
      if (cachedEngine.getState().isProcessing) continue;
      detachEngine(cachedId);
      engineCache.delete(cachedId);
    }
  }
  ```
- **现状:** `await` gap between `setActiveId` and `setActiveEngine` with no cancellation token / version guard; post-await eviction uses the closure-captured `id`.
- **风险:** Rapid A→B switching with async (server) storage: A's slow `loadMessages` resolves after B is active → `setActiveEngine(engineA)` shows the wrong conversation, and the eviction loop (closure `id==='A'`) deletes `engineB` from the cache. Persistent `activeId !== activeEngine` inconsistency + duplicate engine on next switch-back. No test covers rapid switching.
- **建议:** Add a cancellation/version guard captured per-switch; after `await`, bail if `activeIdRef.current !== id`. Eviction should use the current active id, not the closure-captured one.
- **复核:** Review verdict **保留 P1** (race trace confirmed; no guard/cancellation present; no test).

## [P1-4] All 14 AI renderers omit `data-cid` on their DOM root — inspector/schema bridge broken

_Justification: systematic contract drift against `renderer-runtime.md`; debugger lookup cannot map any AI DOM node to its schema node._

- **文件:** every renderer root, e.g. `renderers/ai-chat.tsx:288-291/311-314/326-329`, `renderers/ai-bubble/index.tsx:98`, `renderers/ai-sender.tsx:150` (+ all 11 others)
- **证据片段:**
  ```tsx
  // ai-chat.tsx — emits testid + data-slot, never data-cid
  <section
    className={cn('nop-ai-chat', props.meta.className)}
    data-slot="ai-chat-root"
    data-testid={props.meta.testid || undefined}
  >
  ```
- **现状:** No AI renderer opts into FieldFrame wrapping (`ai-renderer-definitions.ts` has zero `wrap:` entries), so `node-frame-wrapper.tsx` returns a bare fragment (`frameWrapMode === 'none'`) and does **not** auto-inject `data-cid`. Yet every renderer root emits `data-testid`/`data-slot` but never `data-cid={props.meta.cid}`. `props.meta.cid` is only consumed at `ai-chat.tsx:162` for `componentRegistry.register`.
- **风险:** Violates `docs/architecture/renderer-runtime.md` ("when a renderer owns its DOM root directly, that renderer root emits `data-cid`"; "`cid` belongs on the mounted inspectable node root"). The debugger's `inspectCid` lookup climbs to the nearest `[data-cid]` ancestor and finds none → canvas select/highlight/inspect is broken for the entire AI package.
- **建议:** Add `data-cid={props.meta.cid || undefined}` to each renderer root (matches `content`/`basic` packages, e.g. `alert-renderer.tsx:76`). No schema/contract change.
- **复核:** Review verdict **保留 P1** (contract text unambiguous; confirmed no `wrap:` + fragment passthrough + absent `data-cid`). Kept P1 (not P0) — runtime behavior unaffected; only the dev-tooling bridge is broken.

# Cross-Cutting Patterns

1. **Silent-drop family (drives P1-1, P1-2 + several P2s):** the F1.1 reentrancy guard (correctly) makes `sendMessage`/`setMessages` silently no-op while a turn is in-flight, but several callers (user-edit, sender extension path, attachments upload) don't pre-check `isProcessing` and then clear local state — producing silent data loss. A single "guard callers, not just the engine" sweep would close P1-1 and the sender/attachments P2s together.
2. **Error-fidelity parity (P1-5 + tool-error/matcher P2s):** AI-19 achieved structured `lastError` on most paths, but connector-missing, tool-execution, and bubble-matcher paths still flatten or drop causes. Same theme, different layers.
3. **Per-render object-identity churn (3 P2s):** `ai-chat` rebuilds `componentHandle` / `actionProvider` / `hostScopeData` every render, amplifying subscription storms during streaming. One `useMemo`/ref pass fixes all three.
4. **Public-surface bloat (3 P2s):** dead alias + half-exported extension types + leaked engine internals freeze implementation details as public API with zero host consumers.
