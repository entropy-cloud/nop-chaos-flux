## 详细发现

### [P1] N-1 — 建议 popup 的 `onMouseEnter` 触发"提交"，鼠标悬停即插入并关闭

**一句话理由**：`SuggestionPopup` 把同一个 `onSelect` 回调同时绑到 `onMouseEnter` 与 `onClick`；而 `tiptap-sender` 把 `onSelect` 接到了"插入 mention/slash 命令 + 关闭 popup"的提交逻辑。鼠标移过任一项立即提交，popup 对鼠标用户完全不可用——这不是 hover 预选，是 hover 即 commit。

**位置（pattern）**：

- `rich-text/components/suggestion-popup.tsx:38-53`（popup 项）：
  ```tsx
  <Button
    ...
    aria-selected={idx === activeIndex}
    onMouseEnter={() => onSelect(idx)}   // ← hover 也调 onSelect
    onClick={() => onSelect(idx)}        // ← click 调同一个
  >
  ```
- `rich-text/tiptap-sender.tsx:369-377`（消费方把 onSelect 接到提交）：
  ```tsx
  <SuggestionPopup
    ...
    onSelect={(idx) => popupItems[idx]?.onSelect()}   // ← 这是 commit
    onClose={() => setPopupState({ kind: 'none' })}
  />
  ```
  而 `popupItems[idx].onSelect`（`tiptap-sender.tsx:313-318` / `:324-329`）= `insertMention`/`runSlashCommand` + `setPopupState({kind:'none'})`。

**为什么值得关心**：

1. 用户键入 `@` 打开候选框，把鼠标移向第一项的瞬间，`onMouseEnter` 触发 → 插入第一项 + `setPopupState({none})` → popup 卸载。用户根本来不及看清候选、无法用鼠标选别的项。键盘路径（`handleKeyDown` 的 Arrow/Enter 走 `popupControlsRef`）正常，故 bug 只打鼠标用户。
2. popup 组件没有独立的 `onHover`/`onActiveChange` 出口，只有单一 `onSelect`，消费方又把它当成 commit —— 这是组件契约与消费意图的错位，不是单行笔误。
3. **测试盲区**：`tiptap-extensions.test.tsx:150-176,198-221` 只用 `fireEvent.click(bobItem)` / `fireEvent.click(summarizeItem)` 验证选中，从未 `mouseEnter`/`mouseMove`。绿测给了"popup 可用"的假象。

**信心**：**确定**（wiring 逐行可核对；React `onMouseEnter` 在指针进入元素即派发）。

**建议**：`SuggestionPopup` 增加独立 `onHover?(idx)` 出口用于"高亮预选"，`onMouseEnter` 调 `onHover`，`onClick` 才调 `onSelect`；`tiptap-sender` 把 `onHover` 接到 `setPopupState({...,activeIndex:idx})`。补一条 `fireEvent.mouseEnter` → 断言"不触发 onSelect、仅 activeIndex 更新"的回归测试。

**发现来源视角**：新人开发者（"鼠标移过候选会发生什么"）+ 死代码清道夫（追 onSelect 全链路）。

### [P1] N-2 — Tiptap 发送器 `clearOnSubmit` 在编辑器持焦时失效（Enter 提交不清空）

**一句话理由**：外部清空 effect 以 `editor.isFocused` 为门，但 Enter 提交并不会把焦点移走，于是默认 `submitType:'enter'` + 默认 `clearOnSubmit:true` 下，提交后编辑器文本不清空——一个被现有测试（从不持焦）盖住的回归。

**位置**：

- `rich-text/tiptap-sender.tsx:280-290`（外部清空 effect）：
  ```ts
  useEffect(() => {
    if (!editor) return;
    if (value === lastEmittedRef.current) return;
    if (editor.isFocused) return; // ← 持焦时直接返回，不清空
    try {
      editor.commands.setContent(value ?? '', { emitUpdate: false });
      lastEmittedRef.current = value ?? '';
    } catch {
      /* ... */
    }
  }, [editor, value]);
  ```
- `renderers/ai-sender.tsx:120-124`（Tiptap 的 onSubmit → commit）+ `:59-72`（commit）：
  ```ts
  onSubmit={() => {
    const text = draft.trim();
    if (text.length === 0 || overLimit) return;
    commit(text);          // commit → setDraft('') 当 clearOnSubmit（默认 true）
  }}
  // commit:
  if (clearOnSubmit) setDraft('');   // ← value='' 流向 Tiptap
  ```

**为什么是真的**：用户在 Tiptap 编辑器里按 Enter → submit keymap（`tiptap-sender.tsx:135-154`）调 `callbacksRef.current.onSubmit()` → `commit` → `setDraft('')` → 重渲染 → `value=''` 传入 `TiptapSender`。外部清空 effect 跑：`value('') !== lastEmittedRef(提交文本)` 通过；但 `editor.isFocused === true`（Enter 不 blur，没人调 blur）→ `return`，编辑器文本原样保留。`clearOnSubmit` 静默失效。

**为什么值得关心**：

1. `clearOnSubmit` 默认 `true`（`ai-sender.tsx:51`）、`submitType` 默认 `'enter'`（`:49`）—— 开箱即中招。用户发完一条消息，编辑器里还留着原文，必须手动删才能发下一条。
2. `isFocused` 门的设计意图（避免外部 value 抢占用户正在输入的内容）本身合理，但它无法区分"用户正在打字"与"用户刚提交完"，于是把 `clearOnSubmit` 误伤。
3. **测试盲区**：`tiptap-sender.test.tsx:132-142`「clears the editor when the parent resets value to empty (clearOnSubmit mirror)」从不 `editor.commands.focus()`，所以 effect 跑在"未持焦"分支，绿。没有任何测试覆盖"持焦提交后清空"这条真实路径。这正命中上一轮自评盲区"测试名↔断言诚实度"。

**信心**：**很可能**（wiring 确定如此；唯一不确定项是"Enter 后 ProseMirror view 是否一定仍 `isFocused`"——但 keymap 返回 `true` 仅阻止默认行为，不 blur，parent 也不 blur，故持焦应确定）。

**建议**：在 submit keymap 的 `onSubmit()` 成功提交后，由发送方主动清空（如 `editor.commands.clearContent()` 或在 `commit` 的 Tiptap 分支显式 `setContent('')`），而不是依赖"未持焦"才会跑的外部同步 effect；或在 effect 内对"刚提交"这一来源放宽 `isFocused` 门。补一条"持焦 Enter 提交 → 编辑器清空"的回归测试。

**发现来源视角**：异常路径侦探 + 契约考古（清空契约的隐含前提"提交后焦点会移走"未被兑现）。

### [P2] N-3 — `PROMPTS_DEFAULT_LABEL`：死导出 + 模块加载期 `t()`

`renderers/ai-prompts.tsx:94`：

```ts
export const PROMPTS_DEFAULT_LABEL = t('flux.ai.placeholder');
```

- `rg PROMPTS_DEFAULT_LABEL` 全仓仅此 1 处（声明点），**零消费者**——死公共导出（冻结内部细节为 public API 的同类问题，见兄弟 multi-audit P2 "public-surface bloat"）。
- 该常量在**模块加载时**调用 `t()`。若本模块在 `initFluxI18n(...)` 之前被 import（懒加载/循环依赖场景），`t('flux.ai.placeholder')` 会捕获到错误译文并永久冻结。i18n 译文应在渲染期取，不应在模块顶层求值。
- 因零消费者，当前无实际危害；但一旦有人 import 它即踩中 i18n 顺序陷阱。建议删除该导出。

### [P2] N-4 — mention query 正则含 `\s`，与"no whitespace"注释矛盾

`rich-text/extensions/mention.ts:27`：

```ts
// 行内注释："Match the last `@` that is followed only by word characters (no whitespace)."
const match = textBefore.match(new RegExp(`${MENTION_TRIGGER}([\\w\\s.-]*)$`));
```

字符类 `[\w\s.-]*` 实际**包含** `\s`（空格/制表/换行等），与紧邻注释"no whitespace"相反。后果：`@foo bar` 中 `foo bar` 整段被当作 query，候选框在用户敲空格后仍常驻（`filterMentions` 用子串匹配，可能匹配到带空格的 label）。建议把 `\s` 从字符类移除以兑现注释，或更正注释。

### [P2] N-5 — `user-edit.tsx` 的 `onChange` 形参遮蔽引擎别名 `e`

`renderers/ai-bubble/user-edit.tsx:42` 定义 `const e: MessageEngine = engine;`（为让嵌套闭包拿到非 undefined 类型）；但 `:78` 的 `<Textarea onChange={(e) => setDraft(e.target.value)} />` 形参也叫 `e`，在该回调内遮蔽了引擎别名。当前 `onChange` 不碰引擎，故无 bug；但 `resubmit`（`:55`）依赖外层 `e` 指引擎，一旦有人把引擎调用搬进 onChange 闭包就会静默拿到 event 对象。建议把形参改名（`ev`）或把引擎别名改名（`engine2`）消除遮蔽。

### [P2] N-6 — `ai-suggestions` 用 `item.text` 作 key，重复文案即碰撞

`renderers/ai-suggestions.tsx:93` 与 `:114` 两处 `key={item.text}`。两条建议文案相同时 React key 重复 → 告警 + 可能 state 错乱。与兄弟 multi-audit 已记的 `ai-prompts` 用 `label#index` 同一家族；此处甚至连 index 都没附。建议追加稳定业务 id 或退化到 `text#index`。

### [P2] N-7 — `ai-feedback` 的 like/dislike aria-label 是 emoji，`sources` 硬编码英文

`renderers/ai-feedback.tsx:86-90`：

```ts
case 'like': return '👍';
case 'dislike': return '👎';
case 'sources': return 'Sources';   // 未走 t()
```

- `like`/`dislike` 的可见 label 与 `aria-label` 都是 emoji，屏幕阅读器朗读不一致（同文件其余 action 都走 `t('flux.ai.*')`，唯独这两个用裸 emoji）。
- `sources` 是硬编码英文字面量，未 i18n，与其余 `t()` 调用不一致。建议补 `flux.ai.like`/`flux.ai.dislike`/`flux.ai.sources` 三个 key 并在 `labelFor` 中走 `t()`。

### [P2] N-8 — `highlightJson` token 正则在含转义实体的字符串上失配（高亮缺失，非 XSS）

`renderers/ai-tool-call.tsx:332-343`：流程为 `escapeHtml(pretty)` 后再用 `/(&quot;(?:\\.|[^&]|(?:&quot;))*?&quot;(...))/g` 注入 `<span>`。但 `escapeHtml` 已把串内的 `&`/`<`/`>`/`"` 转成 `&amp;`/`&lt;`/`&gt;`/`&quot;`，而正则的 `[^&]` 一遇 `&` 即停、`&amp;` 又不等于 `&quot;`，故含这些字符的字符串 token 无法被整段匹配，落不到 `tok-str` span（高亮缺失/断片）。**非安全漏洞**（内容已先 escape，无法注入 HTML），纯语法高亮正确性。建议把字符串匹配改为在 escape 前定位、escape 后再注入，或放宽正则以消化实体。

## 跨切面观察

1. **rich-text 子路径是当前最脆的一层，且被"绿测"系统性掩护。** N-1（hover=commit）与 N-2（持焦不清空）都落在 opt-in 的 `./rich-text` 子路径，两个都被现有测试"恰好绕过"——N-1 的测试只 click 不 hover，N-2 的测试不持焦。这正是上一轮 open-audit 自评盲区点名的地方，本轮坐实：rich-text 不仅有边界组合问题，还有"测试名承诺的路径恰好是断言没走的那条"。
2. **"i18n 只在翻译表里"的第二种表现。** 上一轮 O-3（IME）已治了"输入法回车"；本轮 N-3（模块顶层 `t()`）/ N-7（emoji aria-label + 硬编码英文）暴露的是"i18n 取值时机与覆盖面"的缺口——文案层 i18n 到位，但模块加载期求值与 aria-label 还漏。

## 总评（最值得关注的 1-3 个方向）

1. **rich-text 子路径需要一次"鼠标 + 持焦"的端到端回归基线。** N-1/N-2 都不是引擎层问题，而是 Tiptap 集成层的交互/焦点契约问题，且都被单元测试的"理想路径"盖住。建议为 `./rich-text` 补一组专门覆盖 hover、focus-retention、clearOnSubmit-after-submit 的测试，否则下一次重构仍会原地复发。
2. **修复计划应把 N-1/N-2 与兄弟 multi-audit 的 P1-1（user-edit 编辑期重发静默丢字）打包为同一主题——"AI 输入面的提交/清空契约"。** 三者都是"提交"语义在 engine guard / focus gate / hover wiring 三个边界上各被悄悄削弱，单独打补丁会留下不一致。
