# Anatomy Skill 抽象机制分析报告

> 调研日期：2026-10-16
> 范围：`wheresryan22/anatomy`（本地副本 `~/ai/anatomy`，commit `e948829`）—— 一个把技术概念"物化"为可交互等轴测机械图的 Agent Skill
> 关注点：它是**怎么抽象的**，以及**为什么可以抽象**

---

## 1. 结论先行

Anatomy 不是"用 AI 画 SVG 工具"，而是一套**五层抽象栈**：

| 层  | 抽象名              | 输入                                            | 输出                                                       |
| --- | ------------------- | ----------------------------------------------- | ---------------------------------------------------------- |
| L1  | 物化（reification） | 抽象概念（缓存键、GPU context、separable blur） | 一台真实机械（销子锁、龙门绘图仪、床钉盖章+双梳）          |
| L2  | 工作流              | "explain X" 的自然语言请求                      | 十步确定性流程（先真实数字、再造对象、先零件清单、后几何） |
| L3  | 渲染 DSL（kit）     | 零件描述（plan + z + h + tone）                 | 等轴测 SVG（相机、明暗、遮挡序全由 kit 决定）              |
| L4  | 验证（audit）       | "看起来对不对"的审美判断                        | 布尔可判定的几何不变量（无穿透、线有端点、遮挡序正确）     |
| L5  | 模态                | SVG / SVG+WebGL / 3D(beta)                      | 同一 kit、同一相机、同一工艺规则                           |

它能成立有四个根本原因：**软件概念与机械机制同构（都是带约束的状态机）**；**物理直觉是人脑的原生推理域**；**LLM 的能力组合恰好覆盖"求真→造物→编码→自检"全链条**；以及最关键的——**kit 把绘画技能压缩为参数、audit 把质量压缩为布尔**，从而使 agent 的自主迭代成为可能。

---

## 2. Anatomy 是什么

一个标准 Agent Skill（仓库根即 skill 文件夹，`SKILL.md` + `kit/` + `references/` + `examples/`），零 npm 依赖，仅用 Node 内置模块。用户说 `/anatomy explain how a token bucket rate limiter works`，agent 产出一个**等轴测物理对象的可交互图形**：几十到几百个实心零件、四色明暗、正确的由后向前绘制顺序、带标题/提示/实时读数的卡片、缓和的交互动画。三个模态（SVG 为核心；SVG+WebGL shader 画火焰/水波/光晕；3D beta 画真三维旋转件）共享一个 kit。

---

## 3. 它是怎么抽象的

### 3.1 L1 物化层：概念 → 物理对象（一切的总原则）

`SKILL.md` 原文："**The object is the explanation.**"不画盒子、箭头、标签，而是发明一个"其运转机制本身就是该概念"的真实物体。skill 给出的历史映射表：

| 概念                              | 对象                                           |
| --------------------------------- | ---------------------------------------------- |
| 多个 canvas 共用一个 GPU context  | 龙门绘图仪：一个打印头依次造访 16 个墨槽       |
| 缓存键未变则跳过重算              | 销子锁：所有弹子对齐时锁芯转动，且什么都不重画 |
| 7 个不同字节/纹素的 render target | 七斗橱：每个抽屉的深度 = 它的字节数            |
| separable blur（49×49 vs 49+49）  | 床钉盖章 + 两条在导轨上的梳齿                  |
| 依赖朝向的光照                    | 小型照相馆：转盘周围的 key/fill 灯             |

**这不是比喻，是同构映射。** 每个对象零件与概念要素一一对应，每个机械运动与概念状态转移一一对应，每个可见数字来自真实模型（弹簧刚度、量程、转速）。test-rig 例子中：玻璃按钮=被解释的主体；弹簧溜板=回弹；探针=手指；千分表=读数；所有运动由 `rig.ts` 纯模型驱动，读数、aria 文本、图注数字同源。

该层有两个已命名的失败模式及其修复：**too abstract**（漂浮的板/ slab 不构成任何东西→改成抽屉、托盘、卡片架）与 **too flat and bland**（一大平板+几条线→拆成 base/carriage/parts，加槽、螺钉、标尺）。

### 3.2 L2 工作流层：把"生成一张好图"分解为十步

`SKILL.md` 规定严格顺序，且"多数质量在写几何之前就已决定"：

1. **Size it**：Figure（40–80 零件）/ Hero / Epic 分级，先报规模
2. **Truth first**：先收集真实数字与行为，最好写成纯模型模块（`rig.ts`）
3. **Invent the object**：一句话说明什么在动、动意味着什么；禁止临摹参考图
4. **Parts list**：≥40 个零件，分五组（base / structure / mechanism / controls / subject），每个零件坐在另一个零件上
5. **Plan the world**：世界单位≈真实 1px，x/y 在地面、z 向上；选相机方位角/仰角；`fitProjection` 适配
6. **Build geometry once**：静态几何预计算；动件构建一次，用 `translateAlong` 移动；只有形变件逐帧重建
7. **Paint back to front**：画家算法；`A.settle` 测量真实深度并设绘制键
8. **Frame it**：卡片四角（Fig n / 标题 / 提示 / 实时读数）+ 图例 + 图注
9. **Make it live**：指数缓动或真弹簧、空闲巡演、指针/键盘、离屏停止、reduced-motion 静止
10. **Verify like a critic**：headless Chrome 截图、audit 归零、双主题 4× 放大每个接缝、"读每一张 PNG"

这本身就是一种抽象：**把审美转译为可执行清单**。craft.md 的每一条规则都标注了出处——"来自一张被拒或过审的图"。

### 3.3 L3 渲染 DSL 层：kit 把"绘画"压缩为"描述零件"

`kit/iso-kit.mjs`（842 行）是一个极小但完备的等轴测渲染核：

- **固定相机**：`iso([x,y,z], P)` 一个投影函数；`depthOf()` 深度键；`cameraOf({azimuth, elevation})`。方位角默认 45°、仰角 30°，按需 35–60° 微调
- **统一零件语汇**：`{x,y,w,d,r}` 圆角矩形 plan + z + height → `slabOf/extrude` **自动**产出"朝的四色侧面 + 更亮的顶面"；`cylinder / coil / knurl / topTicks / radialTicks / ring / sideArc` 等一整套零件函数；回转体 `lathe.mjs` 用半截面 `[s,r]` 描述任意轴的旋转体；管道线缆 `tube.mjs` 用 route 描述、自动切块
- **语义化明暗（tone hierarchy）**：base/feet=`lo`，structure=`mid`，subject=`hi`，唯一视觉焦点=`lit`。**画什么和怎么画分离**：build 脚本只声明零件的几何与语义，着色与遮挡由 kit 规则决定
- **3D 的数学恒等式**：`turn.mjs` 中"绕竖轴转 θ"**精确等于**"kit 在方位角 a−θ 下画一次"——因为 kit 的光源是相机锁定的。整个 3D 引擎（约 7500 行）由此获得"每次重投影重着色都是 kit 自己的图像"的保真度，且所有屏幕空间审计原样适用于新相机
- **WebGL 同相机**：`gl.mjs` 的 `GLSL_ISO` 把同一台等轴测相机带进 GLSL（`rayOf`、`pixelOf`），shader 在世界空间运行，所以火焰/水波"长在图画里"而非贴在图上；无 WebGL 时 SVG 仍可读

### 3.4 L4 验证层：audit 把"质量"从主观变为可判定

这是 Anatomy 与其他"AI 画图"尝试的分水岭。`kit/audit.mjs`（1913 行）把工艺规则转译成构建期可执行的不变量：

- **几何正确性**：无任何物穿过任何物（clearance，rest/apart/爆炸每帧重放）；每个端点落在真实安装座上（terminals/looseEnds/supports）；弯不捏合、轮廓不自重叠（folds/selfOverlaps）；细长杆视为线，管路不得贴行（crowding）
- **遮挡序为测量而非目测**：构建时每个 item 记录真实形状（`A.recorder`），`A.settle` 对每对重叠物做射线投射求真实深度，`orderKeys` 统一求解。Raptor 首版手工设键留下 323 个深度错误，测量法归零
- **反欺骗**：`coverage` 检查记录形状是否覆盖 ≥60% 的实际绘制（防止用占位形状"骗过"audit）
- **线端检查**：`scripts/lines.mjs` 在 headless Chrome 中断掉所有悬空的缝/刻度/线头
- **3D 轨道审计**：`orbitOrExit` 遍历每个转角、每个运动 clip 帧
- **批评者闭环**：`capture.mjs / drive.mjs / turn-check.mjs` 截图、慢放接触表、逐帧找"pop"，然后要求 agent 读每一张 PNG

其设计哲学直接写在 craft.md："**在几何里修互锁，永远不要用绘制键偏置去修**"——即用根因修复代替症状掩盖。

### 3.5 L5 模态层：三模态同源

SVG / SVG+WebGL / 3D 不是三条产品线，而是同一 kit 同一相机的三个开关。3D 图中"转动的零件每帧重投影重着色，其余保持静态 kit 画作"；WebGL 层夹在前后 SVG 之间。新增模态不需要新观众、新审美、新规则。

## 4. 为什么它可以抽象

### 4.1 概念与机制同构：带约束的状态机

软件/系统概念的形式结构 = **状态 + 转移 + 约束**：缓存键（所有字段匹配才命中）、令牌桶（存量、速率、阈值）、可分离模糊（两次一维 ≈ 一次二维）。机械系统的形式结构同样是状态 + 转移 + 约束：销子锁（弹子列对齐→锁芯可转）、 Printing head（依次造访）、弹簧（刚度/阻尼→回复）。**映射不是修辞而是同构**——锁的运转*就是*缓存命中的运转。这解释了 L1 为何可行、为何"有机制的概念表现强，没有机制的概念表现弱"。

### 4.2 物理直觉是人脑的原生推理域

数百万年进化使人对固体、遮挡、重力、啮合、弹簧有直觉物理（读者"认出机器"即理解，无需学习图例）。而"盒子+箭头+标签"要求读者先习得一套符号系统——这正是 anti-pattern 中 too abstract 失败的根因：**示意图形把理解成本转嫁给读者，物化图形则借用人人已有的模拟器。**

### 4.3 LLM 的能力组合恰好覆盖全链条

- **广博机械知识**：销子锁、千分表（0.01mm 分度）、Raptor 2 试车台、硬币在 30° 斜面上的滚动速度——支撑 "Truth first" 与 "Invent the object"
- **跨域类比**：GPU context 多路复用 → 龙门打印头
- **长指令遵循**：几十条互相冲突的工艺规则（"每条来自一张被拒的图"）能被一致执行
- **大段几何代码一次成型**：85–478 个零件的坐标计算
- **自我批评循环**：4× 放大、读自己的截图、修几何而非修键

其中第 5 点（自检）依赖 L4：**没有可判定的验证，就没有自主迭代。**

### 4.4 kit 参数化"绘画技能"、audit 布尔化"质量"

这是整个体系真正的承重墙：

- **审美被编码为数值**：tone hierarchy（lo/mid/hi/lit）、bevel 0.4–1.6、螺钉点 0.4–0.55、对象占卡片 55–65%、刻度每 4–5 单位。agent 不需要"会画画"，只需要按配方描述零件
- **正确性被编码为不变量**：无穿透、线有端点、遮挡序正确——全部构建期可判定、可归零、不可被目测调参欺骗
- **单一事实源**：读数、运动、aria、图注全部来自同一个 model 模块，"图文不一致"在结构上不可能发生

三者合起来，把原本依赖人类插画师多年训练的任务，转译为一次长会话中的"求真→造物→编码→测量→放大→迭代"循环。**可验证性 = 自主性**，与"AI 能写代码"同构：编译器与测试把代码质量布尔化之后，模型才获得闭环。

## 5. 边界与局限

- 只画机器、仪器、工具、家具；不画人、不画精确地图。无机制可借的概念（纯组织流程、纯数据流）会表现弱
- 不是图表库：无坐标轴、无系列、无数据图
- 慢是故意的：一个图是一整个长会话；3D 轨道审计 30 个零件要 15–20 分钟
- 3D 为 beta；性能上限明显（380 零件手约 20fps@1440p）
- 质量高度依赖 LLM 的知识广度与指令遵循；脱离 kit 与 audit，SKILL.md 的规则不可执行
- 明暗/遮挡是 2.5D 伪三维（真三维仅限 3D 模式的局部零件），不等于通用 3D 引擎（无 three.js 式场景图、光照、后处理）

## 6. 对 nop-chaos flux 的启示（简）

1. **验证先行（INV 思维）**：flux 的 schema/renderer 契约可效仿 audit——把"渲染结果对不对"转译为可判定不变量（数据一致性、字段参与、槽位契约），让渲染器变更可自检
2. **单一模型驱动**：anatomy 的"读数/运动/aria 同源"对应 flux 的"props.props/meta/events 全部来自同一 scope 模型"，继续坚持 renderer 不直连 store 的边界
3. **语义标记优于手写样式**：tone hierarchy 与 flux 的 `data-slot`/marker 类哲学同向——用语义层而非视觉层描述结构，主题/适配由下层统一解决
4. **"对象即解释"的文档范式**：为 flux-guide 的组件文档物化一个最小可运行对象（一台"机器"），比盒子箭头图更降低理解成本
