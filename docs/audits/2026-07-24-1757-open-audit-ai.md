## 详细发现

### [P1] O-1 — 引擎在 `mutate` recipe 之外直接改“被 cached 快照背书”的消息对象

**一句话理由**：`ReactMessageAdapter` 存在的全部理由就是给 `useSyncExternalStore` 提供引用稳定的快照；引擎却绕过 `mutate` 直接改 `getState().messages.at(-1)` 拿到的对象，这正是该 adapter 被设计来防止的快照变异。

**位置（pattern，非孤例）**：

- `engine/create-engine.ts:209-211`（`tool-loop-max` 失败路径）：
  ```ts
  const last = adapter.getState().messages.at(-1); // 读的是 cached 快照里的对象
  if (last) {
    last.metadata = { ...last.metadata, toolLoopMaxReached: true }; // 直接改，未走 mutate
  }
  adapter.mutate('messages', (draft) => {
    /* 仅重建 tail 引用，不重新 copy metadata */
  });
  ```
- `engine/tool-execution.ts:36` + `:61-69`（`executeToolCalls`）：
  ```ts
  const owner = adapter.getState().messages.at(-1); // 同样是 cached 快照里的对象
  // ...在 for 循环里：
  if (!owner.state) owner.state = {}; // 直接改 owner（= state 里的对象）
  owner.state.toolCall = toolCallState; // 直接改
  adapter.mutate('messages', (draft) => {
    draft.messages[ownerIndex] = { ...owner };
  });
  ```

**为什么是真的**：`ReactMessageAdapter.buildSnapshot()`（`adapters/react-adapter.ts:48-56`）返回 `{ messages: this.state.messages, ... }`——**不克隆数组**，故 `cached.messages === state.messages`。于是 `getState().messages.at(-1)` 拿到的 `last`/`owner` 既是内部 state 的对象，**也是已发布 cached 快照里的对象**。在 notify 之前就地改它的 `metadata`/`state`，等于把“上一帧已交付给 React 的快照”从底下改掉。

**为什么值得关心**：

1. 直接违反 `ReactMessageAdapter` 维护的快照不变性（该 adapter 文件 docstring 第一段即为“stable reference between notifications”）。
2. React 19 并发渲染下 `useSyncExternalStore` 可在任意时机重读 `getSnapshot`；快照嵌套对象被中途改写会破坏 tear 检测与 memo 化前提。
3. 作者显然知道需要“fresh reference”（`tool-execution.ts:70-71` 注释明写 “Commit a fresh reference so subscribers re-render”），却**先就地改、后建新引用**——意图与实现错位，证明是重构疏漏而非有意设计。
4. **测试盲区**：`engine-tool-loop.test.ts:151` 只断言 `lastAssistant.metadata?.toolLoopMaxReached === true`（终态值对），`:230-234` 只在 turn 完成后读 `owner.state`（终态）——两者都不校验“是否经由 `mutate` 路径置位 / 快照在执行中途是否被污染”。

**信心**：契约违反 = **确定**；可观测危害（需特定并发渲染时序）= **很可能**。

**建议**：把所有对 `last`/`owner` 的写都搬进 `mutate('messages', draft => { ... })` recipe 内（在 recipe 里 `const t = draft.messages[idx]; t.metadata = {...}`），recipe 完成后由 `notify` 统一重建引用。补一条“执行中途读快照、断言未被就地改写”的回归测试。

### [P1] O-2 — `getMessages()` 返回**活数组**，却以 “Read-only snapshot” 为契约（且同名测试是 fake-green）

**一句话理由**：`getMessages` 的契约与同名测试都承诺“只读快照”，实现却返回内部 state 的同一引用；公开 API `component:getMessages` 和自动保存路径把这条可变别名直接外泄给 host / 异步存储。

**位置**：

- 契约声明：`engine/types.ts:286` —— `/** Read-only snapshot of the current messages (design.md §14.3, ComponentHandle). */`
- 实现：`engine/create-engine.ts:123-125` —— `function getMessages(): ChatMessage[] { return adapter.getState().messages; }`（React adapter 下 = `cached.messages` = `state.messages`，三者同一引用，既不 freeze 也不 copy）。
- 公共外泄 ①：`adapters/ai-component-handle.ts:67-69` —— `case 'getMessages': { const messages = engine.getMessages(); return { ok: true, data: messages }; }`（`data` 即活数组，无 clone）。
- 公共外泄 ②：`adapters/use-conversation.ts:163-168` —— `storage.saveMessages(conversationId, engine.getMessages())`（把活数组喂给**异步**存储实现）。
- fake-green 测试：`engine/__tests__/engine-tool-loop.test.ts:239-246` —— 名为 “getMessages returns a read-only snapshot of current messages”，实际只断言 `length===2` 与 `map(role)`，**不**校验引用隔离、**不**校验“后续引擎变异不反映到旧快照”、**不**校验“改返回数组不污染 state”。

**为什么值得关心**：

1. 与本包自己的 **Decision-A**（`ai-chat.tsx:39-49` 的 `cloneMessages` + docstring “never the live `engine.messages` reference (mutating a projected array would otherwise pollute the engine's internal state)”）**正面矛盾**：包内明明知道引擎数组是活的、对外暴露前必须 clone，唯独 `getMessages`/`component:getMessages`/`saveMessages` 三处公共出口不 clone。
2. host 拿 `component:getMessages` 的 `data` 后 `.push()` / 改字段，**直接写穿引擎内部 state**（Decision-A 明令禁止的行为）。
3. 自动保存把活数组交给异步 `storage.saveMessages`；若实现 `await` 之后再 `JSON.stringify`，期间新一轮 `sendMessage` 已 `push` 新消息，序列化得到的是**跨回合的混合快照**（会话顺序损坏）。
4. 测试名承诺的契约正是被破坏的那个，且断言弱到发现不了——典型的“全绿藏雷”。

**信心**：**确定**（实现、契约、外泄点、弱测试四处可直接核对）。

**建议**：`getMessages` 返回浅拷贝（`return [...adapter.getState().messages]`，或对 message 对象也浅拷以满足“snapshot”语义）；或退一步——把契约改为“live view，调用方自负 clone”，并让 `ai-component-handle.ts` 的 `getMessages` 分支与 `use-conversation.ts` 的 saveMessages 都显式 clone。把 `engine-tool-loop.test.ts:239` 的断言补成真校验（`getMessages() !== internalRef`、改返回数组不影响 `engine.getState()`、后续 send 不改变旧快照）。

### [P1] O-3 — 两条发送路径都缺 IME 组合态守卫，输入法选词 = 提交消息

**一句话理由**：中文/日文/韩文输入法按 Enter 确认候选词时，浏览器派发 `keydown(key='Enter', isComposing=true)`；本包默认 Textarea 发送器与 Tiptap 发送器都不查 `isComposing`，于是“选词”被误判为“提交”——对一个 i18n 为一等公民（`@nop-chaos/flux-i18n` 依赖、整套 skill/doc 语料为中文）的项目是真实回归。

**位置（pattern）**：

- 默认 Textarea 路径 `renderers/ai-sender.tsx:32-38`：
  ```ts
  function shouldSubmit(event, mode): boolean {
    if (event.key !== 'Enter') return false;
    if (mode === 'enter') return !event.shiftKey;   // 不查 event.isComposing
    ...
  }
  ```
  `:81-86` `handleKeyDown` 直接 `if (shouldSubmit(...)) { preventDefault(); handleSubmit(); }`。
- Tiptap 路径 `rich-text/tiptap-sender.tsx`：
  - `:184-205` `handleKeyDown`（editorProps，popup 打开时优先拦截）：`if (event.key === 'Enter') { ctrl.confirm(); return true; }` —— 不查 `isComposing`。
  - `:135-147` 提交 keymap 的 `Enter` 分支：`mode === 'enter'` → `callbacksRef.current.onSubmit()` —— 不查 `isComposing`。
- **全仓校验**：`rg "isComposing|keyCode === 229|composition" packages/`（排除 node_modules/dist）**零命中**——既无 guard，也无任何 IME 测试。

**为什么值得关心**：

1. 这是公认的“中文输入法按回车确认却误提交”根因；标准修复就是 `if (event.isComposing || event.keyCode === 22) return false;`，本包两边都没加。
2. 默认发送器是 Textarea（Tiptap 是 opt-in 子路径），即**默认路径确定受影响**；Tiptap 的 popup-confirm 路径也确定受影响（editorProps.handleKeyDown 在 keymap 之前跑）。
3. `submitType:'enter'` 是默认值（`ai-sender.tsx:45`），即开箱即中招。
4. 上一轮 open-audit 自评盲区明确写了“可访问性仅做了结构性核查，未做键盘全流程操作测试”——本条正是那个盲区漏掉的实锤。

**信心**：Textarea 路径 = **确定**（原生 `keydown` 行为有据）；Tiptap 提交 keymap 路径 = **很可能**（取决于 prosemirror-keymap 内部对组合态的处理；但 popup-confirm 路径与 Textarea 路径已确定无 guard）。

**建议**：`shouldSubmit` 首行加 `if (event.nativeEvent.isComposing || event.keyCode === 229) return false;`；Tiptap 的 `handleKeyDown` 与 Enter keymap 同样加该守卫。补一条 e2e/unit 测试：用 `dispatchEvent` 模拟 `isComposing:true` 的 Enter，断言不触发 `onSubmit`/popup-confirm。

### [P2] O-4 — `ai-attachments` 附件 id 在重复文件上碰撞，`handleRemove` 误删全部

**一句话理由**：附件 id 由 `name-size-lastModified` 派生，同一文件加两次即同 id，导致 React key 重复告警，且 `handleRemove(id)` 用 `filter(a=>a.id!==id)` 把所有同名件一并删掉。

**位置**：

- id 派生：`renderers/ai-attachments.tsx:99` —— `id: \`${file.name}-${file.size}-${file.lastModified}\``。
- key 使用：`:243` —— `<AttachmentItemView key={a.id} ... />`（key 重复 → React 告警 + 可能 state 错乱）。
- 删除：`:125-137` —— `handleRemove` 先 `attachments.find(a=>a.id===id)`（find 命中第一个），但 `:135` `const next = attachments.filter((a) => a.id !== id)`（删掉**所有**同 id 项）。

**为什么值得关心**：用户两次拖入同一文件（常见场景：误操作、或同名不同路径的文件）会触发 React key 警告，且“删一个”变成“删全部”。修复成本低（id 改用 `${name}-${size}-${lastModified}-${crypto.randomUUID()/计数器}`）。

**信心**：**确定**。

**建议**：id 追加一个本地唯一段（模块级计数器或 `crypto.randomUUID()`）。

## 总评（最值得关注的 1-3 个方向）

1. **“全快照契约”是本包当前最脆的硬骨头。** O-1（引擎绕过 `mutate` 改快照背书对象）与 O-2（`getMessages` 返回活数组却谎称 snapshot、且同名测试是 fake-green）是同一主题的两面：**包内已经形成了“引擎 messages 是活的、对外必须 clone”的内规（Decision-A / `cloneMessages`），但这条内规只在 ai-chat 的 hostScope 投影这一处被遵守，在引擎自身的 tool-loop / executeToolCalls 写路径、以及 `getMessages`/`component:getMessages`/`saveMessages` 三个公共出口全部失守。** 这是单一根因（“引擎数组是活引用”这一事实没被一致地编码进契约与测试）的多点外溢，值得做一次系统收敛而非逐点打补丁。

2. **测试“名字 vs 断言”的诚实度需要专项提升。** O-2 的同名测试、O-1 的 `toolLoopMaxReached` 终态断言，都属于“名字承诺的契约恰好是断言没覆盖的那个”。这与上一轮总评第 3 点（接口诚实度）是同一家族，但前轮聚焦在“IO 契约静态校验”，本轮暴露的是“**测试名与测试体之间**也撒谎”。建议把 `contract-honesty.test.ts` 的范围从 import/IO 扩到“测试名宣称的不变性是否真被断言”。

3. **i18n 不是只在翻译表里。** O-3 表明本包把 `flux-i18n` 当成了“文案翻译”，却没把 IME 输入纳入“国际化正确性”。对一个中文语境主导的项目，输入法回车是高频路径而非 edge case。建议把“IME 组合态不触发提交/确认”列入 a11y/i18n 的回归基线。
