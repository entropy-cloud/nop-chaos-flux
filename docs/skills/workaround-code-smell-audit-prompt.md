# 临时方案与坏味道专项审计提示词（Workaround & Code-Smell Audit Prompt）

> Created: 2026-10-10。动因：仓库的修复历史反复出现同一形态——为了尽快让某个问题消失，先用特判、兜底、延迟、复制粘贴或类型断言把症状按住，真正的根因既没有修，也没有登记出口，临时方案随即事实上转正为永久代码。既有的 `code-refactor-discovery-prompt.md` 按**结构维度**全库扫描重构目标，不回答"这段代码是不是在按住一个没解决的问题"；本提示词补这一维：以**临时方案取证**为中心的专项审计，产出物是带根因指认与回归测试要求的重构建议。

## 1. 核心问题与审计范围

本审计只回答一个问题：**这段代码在真正解决问题，还是只是把问题按住了？**

"按住"的判定三要素（同时成立即坐实临时方案）：

1. **症状消失**：报告的问题不再复现。
2. **根因仍在**：产生问题的上游机制没有改变，同类输入换个路径仍会触发。
3. **出口缺失**：没有登记在案的退出条件（关联 bug / plan / issue / 注释里的完成判据），或出口早已过期。

### 两种审计范围

- **模式一：单次修复审计（diff 级）**。刚修完某个问题后自查："这次的修法是不是临时的？"输入为一次 commit / PR 的 diff。重点核对修复是否触达根因、是否在共享代码里留下特判、是否靠兜底让失败路径静默。
- **模式二：范围级扫描（包 / 子系统级）**。对指定范围（整个仓库、某包、某子系统、某批文件）做临时方案普查。重点为十类信号的全量取证与重复代码热区分析。

### 使用方式

把本文整段交给一个 fresh 审查 session（或子 agent），附审计范围与（模式一时）目标 diff。审查必须**先读代码再下结论**；注释、日志、commit message 只作溯源线索，不作为当前状态的结论。

### 审计口径

1. 以 live code 为准，不以历史日志结论为准。
2. 临时方案 ≠ 错误代码。判定必须给出"它按住的真实根因是什么"；指不出根因的，单独标注**根因失传**，这本身就是更严重的发现。
3. 不把动态边界、orchestrator 模式、桥接层天然复杂度、防御式编程的正确用法机械判成坏味道（见 §2 各类的误报排除）。
4. 不把"我个人会写出更好的代码"当成发现；每条发现必须落到 W1–W6 判定基准的某条违约上。
5. 有根因定位的精确修正**不是**坏味道——哪怕是 1px 级修正（先例：tabs 幻影滚动条修复定位到 TabsTrigger `after:` 伪元素伸出 padding 盒 1px，根因清楚、有回归守护）。坏味道的分界线是**根因是否被指认和消除**，不是补丁的尺寸。

## 2. 审查对象：十类临时方案信号

### A. 症状特判（symptom special-casing）

**信号**：

- 条件分支包含无法用领域语义解释的字面量：`if (name === 'xxx')`、`if (index === 0)`、`if (id === 42)`、针对某个具体页面/组件名的例外分支散布在共享代码里。
- 为某一类输入单独走捷径，而不是修正处理该类输入的通用机制。
- 正向白名单/黑名单枚举了"已知会出问题的那几个值"。

**取证**：提取分支条件中的字面量，追问"这个值为什么特殊"；`git log -L` 找该分支的出生 commit，看 message 是否为"修某页/某用例"。

**误报排除**：字面量对应真实领域常量（如协议规定的哨兵值）、schema 显式配置驱动的分支，不算特判。

### B. 防御式掩盖（silent defensive masking）

**信号**：

- try-catch 吞错后返回默认值/空数组继续跑，根因静默。
- 长串可选链 `a?.b?.c?.d ?? 默认值` 把"本应存在却缺失的结构"按住。
- 守卫触发时无日志、无断言、无上报——守卫被触发恰恰证明上游有 bug，静默兜底等于掩盖。

**取证**：枚举 catch 块与 `??` 兜底，逐个问"这个兜底被触发时，谁能知道？"。注意本仓库约定：`void` 调用带 `// Errors routed through <mechanism>` 注释、空 catch 被 ESLint 禁止——**有结构化错误路由的兜底是正确防御**，只有静默吞掉才算掩盖。

**误报排除**：跨信任边界（用户输入、外部数据、宿主环境）的显式校验与降级，且降级路径有观测，不算掩盖。

### C. 时序贿赂（timing bribery）

**信号**：

- 用 `setTimeout` / `setTimeout(0)` / 双重 `requestAnimationFrame` / magic delay（如 `await sleep(200)`）等待另一个系统就绪，而不是建立显式就绪信号或订阅。
- 轮询 + 固定次数上限（"重试 5 次应该就够了"）。
- 延迟数值带"调出来"的痕迹（150/300/500 这类为通过当前环境测试试出来的数）。

**取证**：对每处延迟问"等的是什么？能否把'就绪'表达为事件、promise 或状态判定？"环境变化（更快/更慢的机器、并发渲染）下该延迟是否可靠。

**误报排除**：动画时序（等待过渡结束后再测量）、有明确协议依据的退避重试，不算贿赂。

### D. 类型系统绕行（type-system bypass）

**信号**：

- `as any`、`as unknown as X`、无解释的 `@ts-ignore` / `@ts-expect-error`。
- 用断言把类型错误压掉，而实际数据结构确实不满足契约——类型系统在如实报警，断言在销毁证据。

**取证**：逐个检查断言两侧的真实类型；能改数据结构/收窄类型/加判别联合而改掉断言的，即为绕行。

**误报排除**：动态边界（schema 反序列化、第三方库无类型、JSON parse 结果）上一次性的、带注释说明依据的收窄断言是合理用法。

### E. 强制刷新与 DOM 突袭（force-remount & DOM raid）

**信号**：

- `key={Math.random()}` / `key={Date.now()}` 强制重挂载以"解决"状态残留。
- 手动 `window.location.reload()`、手动 `dispatchEvent` 模拟用户操作驱动内部逻辑。
- React 渲染器里 `querySelector` / `getElementById` + 直接改 `style` / `textContent`，绕开数据流。
- 事件订阅"先 off 再 on"来压重复触发，而不是修订阅生命周期。

**取证**：问"状态为什么会残留/事件为什么会重复？"——这些 hack 的存在本身就指认了一个未被修复的所有权或生命周期 bug。

**误报排除**：宿主集成边界（第三方 DOM 库挂载点、画布/编辑器容器）内受控的 DOM 访问；性能敏感路径上有注释的逃生舱。

### F. 视觉补偿（visual compensation）

**信号**：

- 无注释的像素级 nudge：`mt-[-1px]`、`translate-y-[0.5px]`、`left-[-2px]`，用来对齐本应自然对齐的结构。
- `z-index` 抬升压住本不该重叠的元素；`overflow-hidden` 掩盖内容溢出；负 margin 抵消他人组件的 padding。
- 布局 bug 没有定位到结构根因（哪两个盒模型约定冲突），而是靠"挪到看不见"收场。

**取证**：对每处 nudge 问"它抵消的是谁的一个什么属性？那个属性为什么在那里？"答不出即补偿。对照本仓库样式契约（布局 renderer 只发 marker 类；渲染器不得隐式布局）判断是否已经越界。

**误报排除**：设计意图内的光学对齐（如图标视觉居中的 -0.5px），有注释或设计令牌依据；上例 tabs 修复（overflow-y-hidden 配对）是根因修复而非补偿。

### G. 测试迁就（test accommodation）

**信号**：

- 为了让测试变绿而放松断言、删除用例、无条件更新快照，而不是排查行为变化是否为回归。
- 产品代码里存在仅为测试服务的分支：`if (process.env.VITEST)`、`if (isTestEnv)`、测试专用 testid 逻辑分叉。
- 测试 setup 里堆叠针对实现的 Mock 链条（mock 掉被测系统本身），测的只是 Mock 的回声。

**取证**：`git log` 查断言/快照修改的 commit 是否伴随产品代码变更；产品代码 grep 测试环境分支。

**误报排除**：时间注入（`now()` 可注入）、端口/路径注入等标准可测性设计不算迁就。

### H. 复制粘贴式增长（copy-paste growth）

**信号**：

- 新需求的实现方式是复制现有文件/函数改几处；同一逻辑出现第 3 份拷贝。
- 多个模块各自手写同一基础设施（promise 缓存、错误剥离、生命周期管理），而不是提取共享原语。已坐实案例（均已收口，作为模式参照）：echarts/ol/zxing 各自手写库加载 promise 缓存（后统一为 `createLazyLibLoader`）；6 个 form-runtime 文件各有一份 strip errors；`action-adapter.ts` 与 `runtime-action-helpers.ts` 各一份 ajax 执行逻辑；`dialog.tsx` 与 `drawer.tsx` 各一份 surface 生命周期管理。

**取证与阈值**：见 §3 重复代码判定协议。

**误报排除**：见 §3 的"不提取"判定问句。

### I. 转正的临时层（promoted scaffolding）

**信号**：

- `TODO` / `FIXME` / `HACK` / `WORKAROUND` / `XXX` / "临时" / "先这样" / "暂时" / "绕过" 注释存在超过若干个迭代，且无关联 bug/plan 编号。
- 迁移期双写、feature flag 永久处于开或关；`legacy-` / `-old` / `-v2` / `-new` 命名长期共存。
- 大段被注释掉的代码（注释化石）。
- 按本仓库废弃流程（`docs/skills/deprecated-feature-cleanup.md`：`@deprecated` + 文档记录在先）本应删除的路径仍在主路径上被调用。

**取证**：字面扫描（§5 第 1 步）→ 对每条命中做 `git log -L` 溯源出生时间与关联单 → 无出口或出口过期即坐实。

**误报排除**：带编号、有 owner、仍在 plan 期限内的登记项；描述"为什么当初这样做、现在为什么安全"的说明性注释（不是待办）。

### J. 声明分裂与漂移（declaration split & drift）

**信号**（2026-10-15 新增；规范源：`docs/architecture/flux-design-principles.md` 原则 7"声明单源与零漂移"）：

- **死声明字段**：契约类型上的可选字段，消费方以防御式读取（`?? {}`、可选链）存在，但全仓生产代码**零声明方**。knip 等未用导出扫描对 interface 可选成员不可见，此类字段可长期存活（判例：`RendererDefinitionShape.propSchema`，仅 2 个 test-support + 12 个测试内联声明，生产零声明）。
- **双声明通道**：同一事实可在两处声明、各自被消费，靠测试/门禁对账而非类型系统约束。判据：同一 key/符号必须同时在两个声明面字段出现——如 `fields` 条目与 `propContracts` 同 key 双写、`eventContracts` 与 `fields(kind:'event')` 同 key、`scopeExportContracts` 与 `injectedLocals` 同符号（判例：`$crud`/`$form` 双声明、`container.onClick` 双声明）。
- **类型手抄副本**：编译面/消费面类型与声明面类型逐字段相同但无类型派生关系（未用 `Pick`/泛型），声明面新增字段时下游**静默漏拷**（判例：`CompiledRendererContract` 手抄 `ValidationContributor`/`RendererValidationDefaults`）。
- **无出口过渡态**：迁移期双读双写、新旧通道并存，且无登记在案的旧通道删除出口（I 类在声明面的特例）。
- **声明面拼错即静默**：注册元数据的字段名/契约 key 拼写错误不产生任何注册期或编译期报错，仅在 CI 期 per-package 测试中间接暴露（声明面缺注册期校验）。

**取证**（本类证据是**跨包聚合事实**，禁止以单模块视野定案或豁免）：

1. **declarator 计数**：对核心契约类型的每个可选字段，`grep -rln "<field>:" packages --include="*.ts" --include="*.tsx" | grep -v "\.test\."`，生产声明为零即死字段候选；再核消费方是否全为防御式读取。
2. **join 检查**：对疑似双通道的两个声明面分别枚举声明文件集，取交集并抽样核对同 key 双写。
3. **结构 diff**：编译面类型与声明面类型逐字段比对；相同而未派生即手抄副本（判别式：给声明面加临时字段，下游不新增即编译报错为合格派生，静默通过即手抄）。
4. **消费方溯源**：从类型字段出发 grep 全部读取点，区分真实消费与防御式兜底读取。

**误报排除**：

- 有登记出口（plan/CX 项）的在途迁移双读不算分裂，但须核出口是否过期——过期即升 P1。
- 字段为预留 API 且 `docs/` 有明确发布计划与 owner 的契约壳，按 `docs/skills/deprecated-feature-cleanup.md` 口径核验后可观察。
- 语义不同的同名字段（不同类型上、各自有生产与消费）不构成双通道。

**裁定规则**：

- 存量坐实（双通道/手抄/死声明）：P1 起评，ROI 裁定**不允许 watch-only 结案**——必须升格 CX-n 工作项或挂接既有收口轨道（现状：`docs/backlog/renderer-metamodel-roadmap.md` RM-0~RM-12；词汇层三债挂 RM-10~12）。
- 新增（原则 7 生效后新合入的分裂/漂移）：P0/P1，直接立案修复或回滚，不接受"以后再收"。
- 死声明字段：删除优先于补声明（方向：删字段 + 删防御读取分支）。

## 3. 大段重复代码判定协议

重复代码是临时方案最常见的沉积形式：每次复制一份，就是一次"不改共享层"的回避。判定分两步。

### 第一步：识别真实重复块

- 口径：**代码块级重复**（结构同构、仅标识符/参数/细节不同），不是概念级重复（同一想法不同名字表达两遍——那归 `code-refactor-discovery-prompt.md` 维度 5）。**例外**：契约/元数据声明面"同一事实两处声明"不属此豁免——它是结构性双通道而非表述重复，按 J 类立案（§2）。
- 建议程序化辅助：对目标范围做 token 归一化（去标识符/字面量/注释）后比对相似度；≥10 行且归一化后相似度高的块对即候选。人工复核结构是否真的同构（控制流、错误处理、边界条件逐一对照）。
- 输出每组的：份数、各份位置（文件:行号范围）、各份之间的已知差异点、估算总冗余行数。

### 第二步：裁定是否为坏味道

对每组重复依次回答三个问句：

1. **同根因吗？** 各份是否实现同一业务/技术机制（会因同一需求变更而必须同步修改）？各自独立演化的巧合相似不算。
2. **已漂移吗？** 各份之间是否已经出现无意的语义差异（一处修了 bug 另一处没修）？已漂移 = 维护成本已经兑现。
3. **提取干净吗？** 提取共享实现后，依赖方向是否仍然符合包层级（`flux-core → … → flux-renderers-*`）？会不会为了共享而把渲染层依赖拖进 core？

**裁定规则**：

- ≥3 份且同根因 → 坏味道坐实，P1 起评（已漂移则升 P0/P1）。
- 2 份、≥15 行、同根因、任一份仍在活跃修改期 → P2；两份都稳定不动 → 可观察。
- 三个问句有任一答"否"，记录误报排除理由，不立案。

不提取是合法裁定：为两份小而稳定的相似实现强行提取会制造早熟抽象和错误的方向依赖。rule of three 是默认阈值，不是硬性义务。

## 4. 判定基准：W1–W6 不变量

每个疑似临时方案必须落到至少一条违约上，否则不立案。

| #   | 不变量       | 判定问句                                                              | 取证读数                               |
| --- | ------------ | --------------------------------------------------------------------- | -------------------------------------- |
| W1  | 根因可指认   | 这段代码按住的真实根因是什么？能否指认到具体机制？                    | 根因描述 + 上游位置；指不出 = 根因失传 |
| W2  | 出口存在     | 有无登记在案的退出条件（bug/plan/issue/注释判据），且未过期？         | 注释编号、issue/plan 链接、登记台账    |
| W3  | 单一事实来源 | 根因修复是否一处改动即可全局生效？还是需要 N 处同步修？               | 同类逻辑份数、同步修改点清单           |
| W4  | 触发可观测   | 兜底/守卫被触发时是否有日志/断言/上报？静默兜底 = 掩盖                | catch/兜底分支内的观测代码             |
| W5  | 删除可回答   | "如果删掉这段会怎样"能否被清晰回答？答不出 = 无人理解，已具备化石特征 | 溯源 commit、关联测试、行为变化描述    |
| W6  | 语义必要     | 特判字面量/魔法值能否被领域语义或 schema 配置解释？                   | 字面量来源、领域常量对照               |

## 5. 审计步骤（取证协议）

范围级扫描按以下顺序执行；diff 级审计跳过第 1、7 步的全量扫描，聚焦变更 hunks。

1. **字面扫描**（秒级，每批必做）：

   ```bash
   grep -rnE "TODO|FIXME|HACK|WORKAROUND|XXX" packages/*/src apps/*/src --include="*.ts" --include="*.tsx" | grep -v test
   grep -rnE "临时|先这样|暂时|绕过|workaround|hotfix" packages/*/src --include="*.ts" --include="*.tsx"
   ```

   每条命中按 I 类取证：溯源出生 commit，查出口状态。

2. **模式扫描**：

   ```bash
   grep -rnE "as any|as unknown as|@ts-ignore|@ts-expect-error" packages/*/src --include="*.ts" --include="*.tsx" | grep -v test
   grep -rnE "setTimeout\(" packages/*/src --include="*.tsx" | grep -v test        # C 类候选，逐个核
   grep -rnE "catch\s*\([^)]*\)\s*\{\s*(return|}\s*$)" packages/*/src             # B 类候选（静默吞错）
   grep -rnE "key=\{(Math\.random|Date\.now)" packages/*/src                       # E 类候选
   grep -rnE "querySelector|getElementById" packages/flux-renderers-*/src          # E 类候选
   grep -rnE "mt-\[-|translate-[xy]-\[0?\.|left-\[-|top-\[-" packages/*/src        # F 类候选（像素 nudge）
   grep -rnE "process\.env\.VITEST|isTestEnv|NODE_ENV.*test" packages/*/src --include="*.ts" --include="*.tsx" | grep -v test   # G 类
   ```

   命中即候选，逐个人工核对（§2 各类的取证方法），禁止按 grep 结果直接定案。

3. **git 考古**：对每个候选块 `git log -L <start>,<end>:<file> --oneline`（或 `git blame -L`）找出生 commit；commit message 含"临时/规避/先凑合/绕过"或只描述症状（"fix: xxx 页面不显示"）而无根因描述的，是 W1 失败的强信号。

4. **重复块识别**：按 §3 第一步做归一化比对（可用脚本辅助，人工复核同构性），产出重复组清单。

5. **声明面分裂扫描**（J 类，2026-10-15 新增；每批必做，证据为跨包聚合事实——按批裁剪范围但不得以批内视野豁免）：

   ```bash
   # 对本批触及的核心契约类型（RendererDefinitionShape / BaseSchema / CompiledRendererContract 等）的
   # 每个可选字段做生产声明计数（零生产 = 死字段候选，转 §2.J 取证第 1 步）
   grep -rln "<field>:" packages --include="*.ts" --include="*.tsx" | grep -v "\.test\."
   # 疑似双通道的两声明面分别枚举后取交集，抽样核同 key 双写
   ```

   另核编译面类型是否派生自声明面（§2.J 取证第 3 步结构 diff）。存量坐实按 J 类裁定规则升格 CX/收口轨道，不允许 watch-only 静默结案。

6. **辅助门禁交叉核对**：`pnpm check:audit-suspects`、`check:audit-async-failure-paths`、`check:audit-hardcoded-type-dispatch`、`check:oversized-code-files` 等既有门禁的输出作为线索源；门禁红线（已登记的 pre-existing 项）不重复立案，但其中的临时方案可被本审计升级定性。注意 knip 类未用导出扫描对 **interface 可选成员死字段**不可见——J 类不以其为豁免依据。

7. **范围结构走读**：抽读范围内核心实现文件，捕捉 grep 抓不到的信号（按流程写的复制粘贴、被注释的分支、顺序耦合）。禁止只看 barrel / README 下结论。

8. **误报排除复核**：汇总前逐条对照 §2 误报排除与 W1–W6，剔除合理防御、动态边界、有根因的精确修正、stable 双份重复。

9. **汇总输出**（§6）。

## 6. 输出格式

### 单条发现模板

```
### [类别A-J] 简短标题
- **位置**: `packages/xxx/src/yyy.ts:120-145`
- **严重度**: P0 / P1 / P2 / P3
- **现状**: 这段代码做了什么（一句话）
- **按住的根因**: 真实问题是什么、在上游哪里；不可考则写"根因失传"
- **违约基准**: W1-W6 中的哪条（可多条）
- **为什么是临时方案**: 按三要素（症状消失/根因仍在/出口缺失）对照说明
- **风险**: 不处理的后果（回归面、漂移面、演进阻力）
- **重构方向**: 根因修复方案一句话 + 需要的回归测试
- **重复组**（仅 H 类）: 份数、各份位置、总冗余行数、漂移证据
- **声明面聚合证据**（仅 J 类）: declarator 计数、生产/消费 join 结果、派生关系 diff、漂移证据
- **ROI 裁定**: 立即重构 / 排期进 plan / 挂账观察（观察项必须登记台账，不允许静默；J 类存量坐实不允许 watch-only 结案）
- **误报排除复核**: 为什么不是合理防御/动态边界/精确修正
```

严重度标准：

- `P0`：临时方案已在制造错误行为，或静默兜底已实际吞掉真实故障；原则 7 生效后新合入的声明分裂/漂移。
- `P1`：无出口的转正临时方案；已漂移的重复组；≥3 份同根因重复；根因失传项；存量坐实的声明分裂（双通道/类型手抄/死声明字段）。
- `P2`：双份大块重复且仍在活跃修改；出口过期；局部症状特判。
- `P3`：观察项（稳定双份重复、轻微 nudge 无注释、低风险遗留注释）。

### 汇总要求

1. **转正清单**：所有 W2 违约（无出口）项，按风险排序——这是"临时"已经变"永久"的部分。
2. **重复代码热区**：按总冗余行数排序的重复组清单，标注漂移证据。
3. **Top 重构建议**（默认 3 项）：本轮最值得立即做的重构，每项写明：根因修复点、预期删除的临时方案本体、回归测试要求、预估影响面。
4. **误报排除清单**：看起来像问题但裁定不动的，附理由——防止后续审计重复立案。
5. **范围整体判断**：该范围的问题是零星个案，还是系统性在用临时方案换进度（后者需在 roadmap 层面对策）。

## 7. 重构衔接与门槛

1. **test-first 先行**：重构前先写钉住现有正确行为的回归测试（临时方案存在往往意味着该行为当前无测试约束），再动结构。执行参照 `docs/skills/test-first-implementation-prompt.md`。
2. **删除本体**：每个重构项完成的判据包括对应临时方案本体被删除（特判分支、延迟、断言、注释化石），不得"只加新层不清旧层"。清理走 `docs/skills/deprecated-feature-cleanup.md` 流程（如涉及公共面）。
3. **保护区门槛**：涉及 `packages/flux-core/src/`、schema/contract validation、renderer 定义字段、样式契约的重构建议，按 `docs/context/ai-autonomy-policy.md` 为 plan-first——审计只产出建议，不直接实施。
4. **记录归档**：根因失传项坐实后按 `docs/bugs/00-bug-fix-note-writing-guide.md` 补记；成批重构进 `docs/plans/`（遵循 plan authoring guide）。
5. **验证闭环**：重构落地后按仓库验证清单跑五门禁（typecheck / build / lint / test / check），e2e 与单测全绿时按 AGENTS.md 记录 full-green 状态。
