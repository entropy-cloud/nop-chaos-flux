## validate.ts 拆分 Decision（P2-BND-1）

**裁定：移交 HCA-CG（跨层行数治理集中批次），不在本 plan 落地拆分。**

### Why Not Blocking Closure

1. **阈值性质**：validate.ts 524 行处于 WARN 桶（500<524≤700），距 ERROR 硬门禁（700）有 36% 余量；非 CI 阻塞（`check:oversized-code-files` WARN 不 fail）。HCA3 dirty-collector 665 行（WARN 桶高位）已落地拆分因其承担三职责；validate.ts 承担**单一职责**（config 校验），内聚性高。

2. **拆分收益/风险比低**：524 行的构成 = 主入口（:406-459，54 行）+ 6 per-shape 校验器（:86-404，319 行）+ 3 helper（:10-78，69 行）+ 2 legacy 扫描器（:469-523，55 行）+ 常量/类型（:1-8,80-84，27 行）。per-shape 校验器共享 helper（isPlainObject/isPrimitive/assertShape/checkNumberField/checkStringField）——抽出 validators/ 须同时抽 helpers/，524 行拆 3+ 文件 = 过度碎片化，增加导入/导航开销换取 24 行阈值的边际收益。

3. **公共面无影响**：validate.ts 不在包 index.ts 公共导出（仅 `serializeScadaConfig` 经 index 导出）；validateScadaConfig 经 internal path `../serialization/validate.js` 被 engine/binding/editor/renderer 消费，拆分不改变公共 API。

4. **owner 归属正确**：HCA-CG（Guard 沉淀 / 行数治理）是集中治理超阈值文件的指定批次（roadmap §HCA-CG）。borderline 单文件（510-540 区间）宜在 HCA-CG 聚合裁决（若多文件同区间，协调拆分 pass 比逐 plan 拆更高效）。

### 拆分缝（HCA-CG 执行时采用）

若 HCA-CG 裁定拆分，按以下缝执行（与 HCA3 dirty-collector 拆分同型 Decision）：

- `serialization/validators/`（新目录）：6 per-shape 校验器（validateBinding/validateAnimation/validateStateDeclaration/validateSymbolEvent/validateSymbolNode/validatePointDeclaration）+ 共享 helper（isPlainObject/isPrimitive/assertShape/checkNumberField/checkStringField/ANIMATION_KINDS/SYMBOL_EVENT_ONS）→ `validators/index.ts` + `validators/helpers.ts` + 按需拆 `validators/symbol-node.ts`（validateSymbolNode 最大，:211-346）。
- `serialization/legacy-scan.ts`（新文件）：scanSymbolLegacy + scanLegacyAtSyntax + LEGACY_AT_PATTERN + MAX_VALIDATE_DEPTH。
- `serialization/validate.ts`（保留瘦主入口）：validateScadaConfig 主入口 + `export type ScadaValidationResult` + `export { ... } from './validators/index.js'` + `export { ... } from './legacy-scan.js'` re-export（**公共导出面 `validateScadaConfig`/`ScadaValidationResult` 签名与导出位置不变**）。
- 各文件目标 ≤ 500 行 WARN 桶清零；`serialization-validate.test.ts` 全量回归转绿（测试 import 不变，仍从 `./validate.js`）。
