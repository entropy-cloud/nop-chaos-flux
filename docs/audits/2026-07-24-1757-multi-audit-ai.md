## P1 Findings — material defects / contract drift (should be fixed)

### [P1] abort→send race clobbers the new turn's controller and requestState

**Justification:** Real correctness defect — a stale turn's `finally`/`catch` unconditionally clears `abortController` and overwrites `requestState` for a turn that started after abort, leaving the live stream uncancellable and the UI showing a stale terminal state. Triggered by programmatic back-to-back `abort()→sendMessage()` (schema action chains, regenerate-after-abort).

- **File:** `packages/flux-renderers-ai/src/engine/create-engine.ts:284-291` (finally), `:276-283` (outer catch), `:400-407` (runOnce catch)
- **Evidence** (finally — no identity guard):
  ```ts
  } finally {
    adapter.mutate('full', (draft) => {
      draft.abortController = null;   // no check that draft.abortController === abortController
    });
    for (const plugin of plugins) {
      await plugin.onTurnEnd?.(buildContext(abortController));
    }
  }
  ```
  Contrast with the success path which has a _partial_ value-guard only:
  ```ts
  adapter.mutate('requestState', (draft) => {
    if (draft.requestState === 'aborted') return; // checks value, not controller identity
    draft.requestState = 'completed';
    draft.isProcessing = false;
  });
  ```
- **Race scenario:** Turn A streaming → host `await engine.abort()` (sets `isProcessing=false` synchronously at `:445-448`) → host `await engine.sendMessage('next')` → turn B passes the `isProcessing` guard (`:168`), installs `controllerB` (`:189`) → turn A's `runOnce` catch + `runTurn` finally resume on the next microtask → finally sets `abortController=null` (clobbers `controllerB`), catch/finally set `requestState='aborted'`/`isProcessing=false` over turn B's live `'processing'`.
- **User-visible failure:** (1) Stop button becomes a no-op (`abort()` reads `getAbortController()` → `null`); (2) UI shows `aborted`/`completed` while a new message streams underneath; (3) `useConversation` auto-save snapshots a half-streamed list.
- **Recommendation:** Add controller-identity guards to the catch and finally blocks: `if (draft.abortController === abortController) draft.abortController = null;` and an early-return guard `if (draft.abortController !== abortController) return;` in the catch/completion mutates. Mirror the pattern already used for the success-path check.
- **Test gap:** `engine/__tests__/engine-concurrency.test.ts` tests the `isProcessing` guard during streaming but **no test** exercises the `abort()→sendMessage()` interleave while turn-1's generator is still gated. A reader would reasonably conclude turn serialization is fully proven — it is not.
- **False-positive exclusion:** Not a benign "host should not do this" — `regenerate()` (which the engine exposes) itself does abort-truncate-resend, and schema `component:abort`→`component:sendMessage` chains are a documented capability. The AI-01 comment at `:163-167` explicitly states the intent to serialize turns; this is an unfulfilled contract.
- **Dims:** 06, 19, 23

### [P1] `hostScopeData` clones the full message array on every streaming chunk, contradicting the documented turn-boundary snapshot

**Justification:** The code's own comment claims a turn-boundary memo but no memo exists; React Compiler cannot help because `messages` is a new array reference every chunk. Per-chunk `structuredClone` + `scope.replace` causes unnecessary deep-clone work and descendant re-renders during streaming.

- **File:** `packages/flux-renderers-ai/src/renderers/ai-chat.tsx:173-185`
- **Evidence:**
  ```tsx
  // The memo recomputes on `isProcessing` transitions (turn boundaries) — the
  // projected copy is intentionally a point-in-time snapshot, not a live feed
  const hostScopeData = {
    isProcessing,
    messages: cloneMessages(messages), // structuredClone — runs every chunk
    activeConversationId,
  };
  const hostScope = useHostScope(hostScopeData, props.path, 'ai');
  ```
  `useHostScope` (`packages/flux-react/src/workbench/hooks.ts:88`) runs `scope.replace?.(scopeData)` in a `useLayoutEffect` keyed on `scopeData`.
- **Current state:** During streaming, `useMessage` re-renders on every chunk → `messages` is a fresh array ref → `cloneMessages` deep-clones the entire conversation → `scope.replace` fires → every descendant reading `${messages}` re-renders. The comment claims turn-boundary behavior; the implementation is per-chunk.
- **Risk:** Deep-clone cost scales with conversation length (not chunk size); descendant re-renders fire per token. On long conversations this is measurable jank. Also a contract-drift: a host reading `${messages}` mid-stream expecting a stable-between-turns snapshot (per Decision-A) receives a live per-chunk view.
- **Recommendation:** Gate the clone explicitly on `requestState` terminal transitions (`completed|aborted|error`), or snapshot only when `isProcessing` flips `true→false`. Hosts needing the live set already have `component:getMessages`.
- **False-positive exclusion:** The clone-itself (Decision-A isolation) is correct and must stay; only the per-chunk frequency is wrong.
- **Dims:** 05, 07

### [P1] `ReactMessageAdapter` snapshot-identity contract has zero direct assertion (fake-green risk)

**Justification:** The adapter's sole reason to exist is the cached-snapshot optimization for `useSyncExternalStore`; if someone "simplified" it to always rebuild, every existing test stays green but production hits infinite-render loops.

- **File:** `packages/flux-renderers-ai/src/adapters/react-adapter.ts:22-46`
- **Evidence:**
  ```ts
  private cached: PublicMessageState | null = null;
  override getState(): PublicMessageState {
    if (this.cached === null) {
      this.cached = this.buildSnapshot();
    }
    return this.cached;
  }
  ```
- **Current state:** ~6 test files exercise `createReactMessageAdapter` but only assert _values_ after `act()` flush. No test asserts `adapter.getState() === adapter.getState()` (same ref between mutations) or that the ref changes after `mutate`.
- **Risk:** The defining invariant is trusted, not proven. A refactor dropping `this.cached` passes all tests and silently breaks React 19 `useSyncExternalStore` (infinite render loop / tear detection).
- **Recommendation:** Add a focused unit test: (1) `getState()` returns same ref across repeated calls with no mutation; (2) after `mutate('messages', …)`, returns a _different_ ref; (3) cached `messages` array ref stable across reads, flips on messages-kind mutation.
- **False-positive exclusion:** `state-adapter.test.ts` covers `BaseMessageStateAdapter` kind-routing but not `ReactMessageAdapter.cached`.
- **Dims:** 14, 23

## Considered and Dismissed (false positives avoided)

1. **`componentHandle` / `actionProvider` per-render churn** (dims 04/05/07 sub-agent flagged as P1): **DISMISSED.** React Compiler is enabled (`babel-plugin-react-compiler@1.0.0` + eslint `error`). `createAiComponentHandle`/`createAiActionProvider` are pure factories returning plain objects with closures over stable inputs (`engine`, `conversationController`, `id`, `name`). The Compiler auto-memoizes these → stable identity → `useEffect`/`useNamespaceRegistration` do not re-run. AGENTS.md explicitly states "Do not add `useMemo` by default." Flagging missing `useMemo` here would be a false positive against the project's Compiler baseline.
2. **`void engine.abort()` / `void events.onXxx()` fire-and-forget** (suspect `void-promise-no-catch`): **DISMISSED.** `engine.abort()` is internally safe (sync `controller.abort()` + sync `mutate`); the in-flight `runTurn` catch handles the stream rejection. Event dispatches are host-notification boundaries where the engine must not crash on a buggy host handler. Documented convention.
3. **Bare `catch {}` parsing guards** (`ai-attachments`/`ai-bubble`/`ai-tool-call`/`ai-voice-input`/`tiptap-sender`): **DISMISSED.** All guard benign operations (`URL.revokeObjectURL`, `JSON.parse`/`jsonrepair` with documented fallback, `recognition.abort()` on unmount, Tiptap `setContent` lifecycle) with correct fallback behavior. Comments document each.
4. **`catch(error)` structured dispatcher catches** (`ai-component-handle.ts:88`, `use-conversation.ts` storage catches): **DISMISSED.** Component-handle catch preserves the original error in `{ ok:false, error }`. Storage catches route through `reportStorageError` (host callback + console.warn) — AI-28 observability, tested.
5. **AbortController plumbing / concurrent-send guard / signal forwarding / maxToolRounds**: **VERIFIED CORRECT.** Controller created per-turn before first `await`; abort idempotent; `isProcessing` guard present; signal forwarded to connector + tools; `maxToolRounds` enforced. (The abort→send race above is a _gap_ in these guards, not their absence.)
