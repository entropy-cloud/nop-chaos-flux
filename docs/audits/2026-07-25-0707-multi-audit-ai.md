## [P1-1] `deleteConversation` post-await stale-closure race — same family as prior P1-3, missed method

_Justification: real state-corruption defect on a plausible user flow (delete a streaming conversation + concurrent create/switch); the prior P1-3 fix introduced `activeIdRef` but applied it only in `switchConversation` — `deleteConversation` was missed and still reads closure state after an await gap._

- **File:** `packages/flux-renderers-ai/src/adapters/use-conversation.ts:326-344`
- **Evidence:**
  ```ts
  async function deleteConversation(id: string): Promise<void> {
    setConversations((prev) => prev.filter((c) => c.id !== id));
    const removed = engineCache.get(id);
    detachEngine(id);
    engineCache.delete(id);
    if (removed && removed.getState().isProcessing) {
      await removed.abort();            // ⚠ AWAIT GAP
    }
    if (activeId === id) {              // ⚠ closure activeId — stale post-await
      const next = conversations.find((c) => c.id !== id) ?? null;  // ⚠ closure conversations — stale
      setActiveId(next?.id ?? null);
      setActiveEngine(next ? (engineCache.get(next.id) ?? null) : null);
    }
    ...
  }
  ```
- **Current:** The `if (activeId === id)` check and the `conversations.find(...)` lookup both read **closure-captured** state (frozen at the render that created this `deleteConversation`). After the `await removed.abort()`, React may have processed one or more renders in which a concurrent `createConversation` or `switchConversation` updated `activeId` and `conversations`. The stale reads then queue `setActiveId(...)` / `setActiveEngine(...)` updates that **override** the concurrent action's updates (React applies them later in batch order).
- **Risk:** Concrete failure trace — conversation X is mid-stream, user clicks "delete X", during the abort's await gap the user clicks "new conversation" (Y): the post-await closure read sees `activeId === 'X'` (true) and `conversations === [X]` (so `next === null`), then calls `setActiveId(null)` + `setActiveEngine(null)` — overriding `createConversation`'s `setActiveId('Y')`. End state: a Y conversation exists in the list but the UI shows no active conversation. Same defect class as prior P1-3 (post-await stale closure in conversation lifecycle). The fix infrastructure (`activeIdRef` at `:126`) is already in the file but unused here.
- **Fix:** Mirror the P1-3 fix — read `activeIdRef.current` instead of closure `activeId`, and read conversations from a ref or accept that the closure is "good enough" only when no concurrent mutation happened. Concretely: `if (activeIdRef.current === id)` plus `setConversations(prev => ...)`-style functional update for the `next` lookup. Add a regression proof that runs delete-during-abort + concurrent create and asserts the new conversation becomes active.
- **Not a false positive because:** the closure-captured `activeId` is unambiguously read on line 334 after the `await` on line 332; the `activeIdRef` mirror on line 126 exists precisely to fix this class of bug (per the P1-3 remediation comment block at `:117-129`) but is not consulted by `deleteConversation`. The existing `use-conversation-create.test.ts:38-51` test only covers the trivial "delete the only conversation" case — no concurrent mutation during the abort await.
- **复核:** live code confirmed (line numbers, await gap, closure read, missing `activeIdRef` consult, absent regression test).

## [P1-2] `ai-citations` sanitizes then renders as React text → HTML entities are double-encoded and visibly mangled

_Justification: visible display corruption on common AI output (math comparisons, code explanations, any text containing `<`, `>`, or `&`); `sanitizeHtml` HTML-encodes its output, but the renderer feeds that encoded string to React as text content, which re-escapes the `&` — the user sees literal `&lt;` / `&gt;` / `&amp;` instead of `<` / `>` / `&`._

- **File:** `packages/flux-renderers-ai/src/renderers/ai-citations.tsx:63-85`
- **Evidence:**
  ```tsx
  const rawText = extractMessageText(message);
  if (!rawText) return null;
  const safeText = sanitizeHtml(rawText);          // DOMPurify HTML-encodes: "5 < 3" → "5 &lt; 3"
  const segments = parseCitations(safeText);
  return (
    <div ...>
      {segments.map((seg) =>
        seg.kind === 'text' ? (
          <Fragment key={seg.id}>{seg.text}</Fragment>   // React re-escapes "&" → user sees "5 &lt; 3"
        ) : ( ... )
      )}
    </div>
  );
  ```
- **Current:** `sanitizeHtml` (from `@nop-chaos/flux-renderers-content`) runs DOMPurify with `USE_PROFILES: { html: true }`, which HTML-encodes `<`, `>`, `&` in text nodes (e.g. input `"5 < 3"` → output `"5 &lt; 3"`). The sanitized string is then handed to React as **text content** (`{seg.text}`), which auto-escapes the `&` again — the DOM ends up with `5 &amp;lt; 3` and the browser renders the literal string `"5 &lt; 3"`. Verified empirically: `DOMPurify.sanitize('5 < 3 and a > b', { USE_PROFILES: { html: true }, FORBID_TAGS: ['style'] })` returns `"5 &lt; 3 and a &gt; b"`.
- **Risk:** Any assistant response containing `<`, `>`, or `&` outside HTML tags (extremely common in math, code explanations, comparisons, logical operators, links) displays with literal `&lt;` / `&gt;` / `&amp;` text in the inline-citations renderer path. The existing XSS test (`ai-citations.test.tsx:90-117`) only asserts `container.querySelector('script')` / `('b')` / `('[onerror]')` are null — it never asserts `container.textContent`, so the display corruption is invisible to the suite. The markdown path (`ai-bubble/renderers/markdown.tsx:35`) is unaffected because `react-markdown` re-parses entities; only the citations-text path is broken.
- **Fix:** Drop `sanitizeHtml` for the inline-citations text path — React's text rendering already escapes `<`/`>`/`&` safely (no XSS exposure from a plain string child). If tag stripping is genuinely needed (the test at `:106` expects `<b>` to appear as literal text), use a tag-stripping variant (`html.replace(/<\/?[a-zA-Z][^>]*>/g, '')`) that returns plain text rather than HTML-encoded output. Strengthen the test to assert `container.textContent` contains `"5 < 3"` for that input.
- **Not a false positive because:** empirically confirmed via direct DOMPurify invocation — the output is HTML-encoded; React's text rendering re-escapes; the browser displays mangled entities. This is not the documented markdown-sanitize XSS gap (P2 in prior audit, still live) — it is a different layer (display correctness, not security) in a different file. The prior audit's XSS P2 explicitly carved out the `ai-citations` path as "lower-risk" and only flagged the markdown path; this citations-text double-encoding was not examined.
- **复核:** live code confirmed (sanitize call at `:66`, React text render at `:79`, test gap at `ai-citations.test.tsx:106-116`).
