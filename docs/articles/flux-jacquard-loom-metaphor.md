# 一台提花织机：Flux 的隐喻介绍

> 写作日期：2026-10-16
> 方法：本文按 Anatomy skill 的物化（reification）流程写成——先取真数、再造对象、列零件清单、让运动本身成为解释。方法论注记见文末。

## 1. 为什么是织机

1801 年，Joseph-Marie Jacquard 用一串穿孔卡片控制提花织机：卡片上的每个孔决定哪几根综丝被提起，综丝再决定一组经线的升降。织工不再需要凭记忆逐根提线，**图案变成了一段可以存储、复制、修改的数据**。查尔斯·巴贝奇后来正是从这排穿孔卡片得到启发，把"程序"与"机器"分开——那是整个计算机时代的开端。

一百多年后，我们面对的是同一个问题的下一次出现：

> 用户界面是一张由数据和结构交织出的"图案"。谁来保存图案？谁拿着图案去驱动机器？

百度 AMIS 的回答是：把图案写成 JSON，让渲染器照着织。这个回答足够好，以至于 AMIS 影响深远；但随着图案越来越密、线越来越杂（表达式规则、数据作用域、平行字段、层层透传的 store），织机本身变成了一个需要多年经验才能摆弄的谜物。

**nop-chaos-flux 是同一台织机的彻底重制。** 它保留了"纹版驱动"这个根本决定，重做的是纹版的写法和提花机的机构。这篇文章借一台提花织机，把 Flux 讲清楚。

## 2. 织机全貌：零件与概念一一对应

一台 Flux 之织，零件如下。每个零件都对应 Flux 中一个真实存在的东西，没有装饰件。

| 织机零件                             | 在织机上的作用                             | Flux 中的对应物                                                                          |
| ------------------------------------ | ------------------------------------------ | ---------------------------------------------------------------------------------------- |
| **纹版链**（一连串穿孔卡片）         | 存图案：每张卡片一个图案单元，卡片串成整幅 | **JSON schema**：每个节点一张卡片，父子结构即卡片串接顺序                                |
| **提花机头**（吊针与吊钩）           | 读孔：某孔有孔→提起对应综绳                | **渲染器注册表**（renderer registry）：schema 的 `type` 决定调用哪个渲染器组件           |
| **综框与综丝**                       | 把一根吊绳的分合变成一组经线的升降         | **渲染器与槽位**（slots/regions）：每个渲染器决定自己管的那组 scope 节点显什么、怎么排   |
| **经线**（每根一根，通贯全匹）       | 承载颜色：每根线的颜色参与每个花纹         | **scope 变量**：每个变量一"根"，其值参与每个表达式的求值                                 |
| **梭子与打纬**                       | 每穿一梭、打一次纬，织物进一步             | **事件与动作**：一次交互（click/key）是一次穿梭，action 沿 scope 链派发                  |
| **织物**                             | 最终可见的东西                             | **页面 UI**：数据 × 结构交织出的结果                                                     |
| **卷布辊**                           | 把织好的布收卷输出                         | **React/DOM 输出**                                                                       |
| **花本组织**（织前预编排的穿孔程序） | 把"怎么提线"提前编排好，织时不再思考       | **flux-compiler 的预编译产物**：表达式在编译期变为函数，运行时不再解析                   |
| **边经**（每匹布都有的固定布边）     | 结构性地存在于每匹布两侧                   | **注入的局部变量**（`injectedLocals`，如 `$page`/`$form`）：每个页面天然携带的框架上下文 |
| **断经自停装置**                     | 经线一断，织机立刻停                       | **校验与错误边界**：数据或节点出错时局部停住，而不是织出一匹烂布                         |
| **多把色梭**                         | 换梭即换一整个色系的纬线                   | **15 个渲染器包**：表单、数据、移动、调度、AI……每个领域一匣零件                          |
| **脚踏板**                           | 人的脚给出织造节拍                         | **用户交互**：pointer / keyboard / 空闲巡演                                              |

Flux 的核心工作流——从底层往上，`flux-core` → `flux-formula` → `flux-compiler` → `flux-action-core` → `flux-runtime` → `flux-react` → 15 个 `flux-renderers-*` 包，41 个包、120 余个注册渲染器类型——在织机上就是一条清晰的产线：

> **刻纹版（schema 与编译器）→ 装提花头（注册表）→ 上经整经（scope 建立）→ 开口投梭打纬（渲染与动作）→ 收卷（DOM 输出）。**

## 3. 织机的运转，就是 Flux 的运转

这台织机只需记住一个恒等式：

> **织物 = 经线（数据）× 纹版（结构）**

这正是 Flux 的 `props.props` 契约：渲染器读到的一切"属性值"——label、visible、options——都是经线颜色在纹版孔位上的投影：值由表达式在 scope 中求出，结构由 schema 节点决定。渲染器自己不碰经线（**从不直连 store**），它只在自己负责的那组综框前工作；这是 Flux 给所有渲染器定的家法。

### 纹版：schema 的写法就是图案的写法

AMIS 的纹版有个费解处：同一个属性要分两个孔来记——静态值写 `disabled`，动态值写 `disabledOn`，作者必须记住哪个孔管哪种线。Flux 的做法是**一个孔位，线的性质由织机判定**：`disabled` 一栏里可以放静态值 `true`、可以放表达式 `${$form.submitting}`、也可以放模板串 `"${name} is disabled"`——刻版的人只负责把线接进来，是静线还是活线，由提花机头在读取时自己分辨。判断属于**值**，不属于**纹版的结构**。

这就是 Flux 统一值语义的织机式解释：不靠平行字段翻倍，而靠编译器一处判定。

### 提花机头：type 即综绳

schema 节点上的 `type: 'page'` 不是一段字符串，是一根提绳：它被提起时，`PageRenderer` 这面综框张开，卡片上预留的槽位（regions，如 `title`、`body`）成为开口，子纹版（子 schema）从这里接入。槽位是**预留的开口**——这就是为什么 Flux 说渲染器"渲染子片段用 `props.regions` 而不是自己递归"：经线从既定的开口穿过，织机不为任何人临时剪口。

### 花本组织：编译期与运行期的分工

老式织工织时现想提线顺序；提花织机把提线程序预先编排成花本，织造时只是执行。Flux 把表达式在 flux-compiler 里预先编译——运行时不再解析字符串、不再正则嗅探，只剩执行。图案的"解释成本"被一次性支付在织前，这正是 AMIS 遗留的痼疾（正则自动处理各种 `xxxOn`/`xxxExpr`、深层嵌套不覆盖）与 Flux 的分野：**编译期能决定的，不带入运行时。**

### 边经与断经自停

每一匹布都有布边，`$page`、`$form` 这类注入变量就是 Flux 织机的边经：不需要谁声明，结构性地存在于每匹布两侧。而断经自停装置对应校验与错误边界：一根经线断了（一个字段校验失败、一个节点渲染抛错），织机在局部停下并示意，而不是假装没断、继续织出一匹花案错乱的布。

## 4. 动起来，才真的明白

隐喻的说服力不在静物，在运转。三幕场景，每幕的运动本身就是一条 Flux 核心机制。

### 第一幕：拖动一根经线

把一根蓝色经线抽出，换成红色——织物上**所有**依赖这根线的花位同时变色；不依赖它的地方纹丝不动。

这是 Flux 的响应式更新：scope 中的一个变量改变，订阅它的表达式（`props.props` 里的值、读数、aria 文本）按依赖精确重算，不多织一行。而换色只发生在该发生的地方，是因为综绳只连接它该连接的经线——**依赖关系织在机构里，不靠人盯着。**

### 第二幕：换一卷纹版

把穿孔卡片链整卷换下，装上新的一卷——织机不停机、不重装，开口的位置和次序随新纹版自然改变，落梭即成新幅。

这是 schema 驱动渲染：页面不是一堆命令式摆好的零件，而是纹版与经线在既定机构下交织的结果。换纹版即换页面；机构（提花头、综框、打纬）原样不动。同理，AI 生成一段新 schema 等于送来一卷新纹版——这正是 Flux 的出发点：**当图案的主要生产者从人变成 AI，纹版的写法（显式、可预测、可审查）比机构的灵活性更重要。**

### 第三幕：梭子穿行

踩下脚踏板，梭子带着一纬新线穿过全部开口，打纬将其压紧——每一次穿梭，织物推进一行。

这是一次事件到动作的派发：click 是踏板，action 是梭子，它沿 scope 链穿行（改一个值、触发一段动作流、推开一扇 dialog），所过之处留下新的一纬。梭子的路径由机构决定，不由织工临时比划——事件处理逻辑声明在 schema 的 `events` 上，派发由运行时统一执行。

## 5. 织前车间：纹版在织造之前的事

织机只管织。但在织造之前，还有一间车间——Nop 平台层，基于可逆计算（reversible computation）对纹版做织前处理：i18n 替换、权限裁剪、模块分解与继承、编译期元编程。用织机的话说：

> 同一卷母纹版，可以按订单做**差量修订**——添一段花型、删一组综、换一处注释——生成客户要的那一卷；原卷不动，修订可叠加、可回退、可继承。 Delta 定制不进入织机，这是分层：**能在车间里解决的，不带进织机。**

## 6. 隐喻的边界（诚实声明）

织机讲清了 Flux 的骨架，但它的纬线也有到头处：

- 织物是二维的，而表单状态、校验时序、动作流的分支与条件远比"经纬交错"丰富——这些请看 `docs/architecture/form-validation.md` 与 action 相关架构文档
- 织机一次织一匹，而 Flux 的页面同时在跑空闲巡演、指针、键盘、离屏暂停——运动的完整规则属于运行时层
- 3D 渲染器、AI 会话这类新色梭，不是换色，而是新织法——参见各渲染器包的设计文档

隐喻的职责是把人领到门口，不是替他走完全程。

## 7. 结语

提花织机在历史上的位置，是它第一次让"图案"脱离了织工的手，成为可存储、可传递、可修改的东西。低代码渲染引擎要解决的从来同一个问题：让"界面"脱离逐行摆零件的工匠，成为可存储、可传递、可修改的图案。

Flux 保留了纹版驱动的根本决定，重做了纹版的写法（统一值语义）、提花头的机构（type 即综绳）、织前车间（可逆计算平台层）与自停装置（校验与错误边界）。它是那台织机，在针数密了一百倍之后的样子。
