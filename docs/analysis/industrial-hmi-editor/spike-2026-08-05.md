### 1.2 关键发现：spike-mock-leak 教训触发

**初测 5 场景中 S2/S4/S5 的 FAIL 判定为误判**，根因是 demo 配置不完整：

- ❌ 错误用法：`editor.select(rect)` API 调用 + Rect 无 `editable:true` 声明
- ✅ 正确用法：Rect 必须显式 `editable: true` + 真实点击（pointerdown→pointerup）触发选中

这是 spike plan Failure Path `spike-mock-leak` 的真实复现——**禁以 mock 推断真实 API** 纪律要求穷尽正确用法后才能下裁定。本 spike 经深度探针纠正了初测误判，避免了错误触发 R1 人工确认（否则会错误转向路径 B 自研交互层）。

### 1.3 主路径裁定（E0.1）

✅ **路径 A（leafer-editor 插件底座）在 `tree:viewport + move:drag:'auto'` 配置下成立**

证据链：

1. **深探针 P1（最严格场景）**：`tree:viewport + move:drag:'auto' + editor + editable:true + 真实点击` → Editor 完整接管拖拽，rect 移动 70×60px（150,140 → 220,200 转化为 rect.x:100→170 / rect.y:100→160），viewport 不变。
2. **深探针 P3**：去掉 `move:drag:'auto'` 后 Editor 同样工作 → **`move:drag:'auto'` 非手势仲裁阻断因素**，仅影响空白区拖拽是否触发画布平移（不影响图元拖拽）。
3. **事件流真实抽取**：`editor.select` → `tree.pointer.down` → `tree.pointer.up`（首次点击）→ `tree.pointer.down` → **`editor.move` × 9 帧** → `tree.pointer.up`（拖拽期）。事件序证明 Editor 在选中后接管 pointer 事件、连续派发 editor.move。
4. **viewport 同步正确**：拖拽期间 `app.tree.x/y` 不变，`rect.x/y` 改变 → 手势仲裁精确（图元坐标写入 + 视口矩阵零污染）。

### 2.2 六大事件族真实载荷表

> 字段语义注释基于源码 `leafer-in/packages/editor/src/event/*.ts`（真实类定义，非 mock 推断）。所有事件继承 `EditorEvent` 基类（含 `type/target/editor/worldOrigin/origin/value/oldValue/list`），下列「族特有字段」为各子类新增。

**① EditorMoveEvent**（`editor.before_move` / `editor.move`，TransformTool.move 每帧派发）

```json
{
  "type": "editor.move",
  "moveX": 6,
  "moveY": 5,
  "target": {
    "tag": "Rect",
    "name": "rect0",
    "x": 150,
    "y": 140,
    "width": 100,
    "height": 80,
    "scaleX": 1,
    "scaleY": 1,
    "rotation": 0,
    "skewX": 0,
    "skewY": 0
  }
}
```

- 族特有字段：`moveX/moveY`（number，单帧世界坐标增量，非累计）。基类 `target` 为运行时 Leaf 引用（序列化为 `{tag,name,x,y,width,height,scaleX,scaleY,rotation,skewX,skewY}`）。`list` getter 在 move 事件上为空（move 不重置 value）。

**② EditorScaleEvent**（`editor.before_scale` / `editor.scale`）

```json
{ "type": "editor.scale", "scaleX": 0.87, "scaleY": 0.909,
  "target": { "tag": "Rect", "name": "rect0", "x": 210, "y": 180, "width": 40, "height": 40, ... },
  "worldOrigin": { "x": 250, "y": 220 } }
```

- 族特有字段：`scaleX/scaleY`（number，缩放比）、`worldOrigin`（缩放锚点世界坐标）、`direction`（Direction9 控制点方向）、`lockRatio`（shift 锁比例）、`around`、`transform`（IMatrix `{a,b,c,d,e,f}`，仅多选 simulateTarget 路径填充）、`drag`（仅 scaleWithDrag 路径）。实测：默认 `editSize:'size'` 模式下缩放改写 `width/height`（rect0 宽 100→40）而非 scaleX——适配层读 `target.width/height` 取最终几何。

**③ EditorRotateEvent**（`editor.before_rotate` / `editor.rotate`）

```json
{ "type": "editor.rotate", "rotation": 13.74,
  "target": { "tag": "Rect", "name": "rect0", "rotation": 50.71, ... },
  "worldOrigin": { "x": 230, "y": 200 } }
```

- 族特有字段：`rotation`（number，本帧旋转角度增量，经 `rotateGap:45` 吸附 + float(,2) 精度处理）、`worldOrigin`（旋转中心）、`transform`（多选路径）。`target.rotation` 为累计旋转值。

**④ EditorSkewEvent**（`editor.before_skew` / `editor.skew`）

```json
{ "type": "editor.skew", "skewX": -16.924, "skewY": 0,
  "target": { "tag": "Rect", "name": "rect0", "skewX": -16.924, "skewY": 0, "rotation": 34.254, ... },
  "worldOrigin": { "x": 217.335, "y": 184.521 } }
```

- 族特有字段：`skewX/skewY`（number，斜切值）、`worldOrigin`、`transform`。触发条件：**ctrl+拖拽 resize-line**（`isHoldRotateKey` 进入分支 → `point.name==='resize-line'` → skewing）；ctrl+角点则走 rotate（与 E0.1 §1.4 互斥路径）。

**⑤ EditorGroupEvent**（group/ungroup/open_group/close_group 各 before + 主事件）

```json
{ "type": "editor.group", "editTarget": { "tag": "Group", "x": 100, "y": 100, "width": 300, "height": 80, ... } }
{ "type": "editor.ungroup", "editTarget": { "tag": "Group", "width": 0, "height": 0, ... } }
{ "type": "editor.open_group", "editTarget": { "tag": "Group", "width": 300, "height": 80, ... } }
{ "type": "editor.close_group", "editTarget": { "tag": "Group", ... } }
```

- 族特有字段：`editTarget`（被操作的 Group）。`group()` 返回新 Group（childCount=2，包围盒 100,100,300×80）；`ungroup()` 返回子图元数组（count=2）。命令型事件（非每帧），一次操作一对 before+主事件。

**⑥ InnerEditorEvent**（`innerEditor.before_open`/`open`/`before_close`/`close`）

```json
{ "type": "innerEditor.open", "editTarget": { "tag": "Text", "name": "text0", "x": 520, "y": 100, "width": 62.207, "height": 42, ... }, "innerEditorTag": "TextEditor" }
{ "type": "innerEditor.close", "editTarget": { "tag": "Text", "name": "text0", ... }, "innerEditorTag": "TextEditor" }
```

- 族特有字段：`editTarget`（被内部编辑的目标 UI）、`innerEditor`（IInnerEditor 实例，`innerEditorTag` 取 `innerEditor.tag`，实测='TextEditor'）。触发：**双击**（`openInner:'double'` 默认）含 `editInner` 声明的图元——`@leafer-in/editor` 默认 `UI.editInner='PathEditor'`、`Text.editInner='TextEditor'`，但 PathEditor/TextEditor InnerEditor 需对应插件注册（`@leafer-in/text-editor` 注册 TextEditor）。**前提条件**：InnerEditor 事件依赖 inner-editor 插件装载，仅 `@leafer-in/editor` 不够。

### 2.3 多选框选 + InnerEditor 场景（≥2 非基本场景）

- **多选（shift-click）**：`editor.select` 载荷 `{type, listLen:2, listNames:['rect0','rect1'], valueTag:'Rect'}`——累加选区可靠触发，是多选的稳定路径。
- **selectArea 框选（含发现）**：隔离 `move:'auto'`（重建 `move.drag:false` + `boxSelect:true`）后空白拖拽，**拖拽过程中 selectArea 渐进式选择成功**（editor.select 帧序列峰值 `listLen:5`，listNames=`[b-rect-0..4]`）；但**释放后 finalListLen=0**——释放/tap 处理受 `isMoveMode`/`selectKeep` 默认行为影响清空选区。这是真实 leafer 配置细节（非限制）：E2 设计需 `selectKeep:true` 或自定义 release 处理保留框选结果。复核 E0.1 §1.4 「框选 vs move:drag:'auto' 冲突」：根因有二——① move:'auto' 让位语义使空白拖拽走画布平移（E0.1 已证）；② 即使关闭 move:'auto'，默认 release 行为仍清空框选结果（本节新发现）。
- **InnerEditor**：双击 Text 进入 TextEditor（`innerEditor.open`，innerEditorTag='TextEditor'），`closeInnerEditor()` 退出（`innerEditor.close`）——载荷含 `editTarget`（Text 几何）+ `innerEditorTag`。

### 2.5 flux action 派发链衔接路径评估（对齐 `createNormalizedActionEvent`）

`createNormalizedActionEvent(event)`（`packages/flux-react/src/renderer-helpers.ts:98`）单参数签名：输入对象若有 string `type` → 原样返回；否则合成 `{type:'custom', ...payload}`；null/非对象 → undefined（实测见 `helpers.test.ts:64-147`）。runtime 既有调用先例 `use-scada-events.ts:81` → `createNormalizedActionEvent({ type, ...payload })`。

**关键约束**：leafer Editor 事件虽有 string `type`，但携带**循环/非序列化 Leaf 引用**（`target/editor/value/drag` 均为 Leaf 实例）——**不能直接传入** `createNormalizedActionEvent`，必须先经薄适配层抽取纯 primitive 载荷 + 目标稳定 id（组态 nodeId）。

| 事件族                                           | 衔接路径                                                                                                                                                    | 适配层 cost                         |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| editor.move / scale / rotate / skew              | **需适配层**（高频每帧）：抽取 `{type, ...deltas, targetNodeId}` → createNormalizedActionEvent。**undo-redo 需节流**（仅入栈操作起止帧，非每帧，E2.4 落点） | 小（字段抽取 + nodeId 映射 + 节流） |
| editor.select / hover                            | **直接映射**：`{type, listNodeIds}`                                                                                                                         | 极小                                |
| editor.group / ungroup                           | **需适配层（结构 diff）**：group/ungroup 改变场景树结构 → 映射组态模型 addSymbol/removeSymbol diff（非属性增量）                                            | 中（结构 diff + nodeId 重映射）     |
| editor.open_group / close_group / innerEditor.\* | **直接映射**（低频）：`{type, targetNodeId}`                                                                                                                | 极小                                |

**适配层总 cost = 小～中**：主要工作量在 ① transform 事件族节流 + nodeId 映射；② group/ungroup 结构 diff。无事件「永不派发」风险（gate-3 M-1 教训规避：载荷读取面已逐族真实抽取，字段名/结构确认）。

## E0.3 编辑态覆盖物密集场景性能 spike

### 3.1 测试矩阵与环境

scratch 工程新增 `e0.3.html` + `src/demo-e0.3.js` + `measure-e0.3.mjs`。10 万图元组态（mulberry32 固定种子 42，对齐 runtime `scada-perf-scale-demo.tsx`），Playwright headless Chromium `--use-gl=swiftshader --enable-precise-memory-info`。**测量口径**：fps 经 `app.tree render` 事件计数 + editor.move 帧计数；**内部 rAF 驱动**（page.evaluate 循环）规避 Playwright page.mouse IPC 开销对 wall-clock 的污染（对齐方案 A/方案 B 同口径）。实测数据：`results-e0.3-2026-08-05.json`。

**方案定义**：① 方案 A = leafer Editor 内置覆盖物（EditBox/EditSelect，跟随 Editor 实例，~22 控制点 + simulateTarget）；② 方案 B = 独立 sky Group 自研覆盖物（单 bounding box Rect，对齐 runtime InteractionOverlay「单覆盖物」模式 + 路径 B 自研交互层）。

### 3.2 10 万图元实例化基线

| 指标                    | scratch 实测 | runtime benchmark §3.1 基线                       | 说明                                                                          |

| 10 万图元构建 buildMs   | **239 ms**   | 373.1 ms（含 runtime registry/样式解析/组态构建） | scratch 单层 App 更快（无 runtime 开销），对齐 I1.2 spike 与 runtime 差异先例 |

### 3.3 覆盖物挂载形态两方案实测对比（密集度梯度 10/100/1k/10k 选区）

> 候选阈值：编辑态拖拽响应 ≥30fps（低于运行态 ≥45fps 红线，`editor-initiation.md §5.2`）。headless+swiftshader 为下界（真实 GPU 浏览器数值更高，候选偏保守）。

| 选区 n | 方案 A moveFps | 方案 A renderFps | 方案 A editor.move syncAvg | 方案 B renderFps | 差距 (B−A) |
| ------ | -------------- | ---------------- | -------------------------- | ---------------- | ---------- |
| 10     | **48.7**       | 49.8             | 9.0 ms                     | 48.4             | −0.3       |
| 100    | **50.2**       | 51.3             | 8.4 ms                     | 49.3             | −0.9       |
| 1000   | **50.2**       | 51.2             | 9.7 ms                     | 49.2             | −1.0       |
| 10000  | **32.2**       | 33.3             | 20.3 ms                    | 36.4             | +4.2       |

**关键观察**：

1. **≤1k 选区**：两方案持平（~50fps，远超 30fps 候选），方案 A 的 simulateTarget + editBox 开销在中小选区可忽略。
2. **=10k 选区**：两方案均回落至 30–37fps 区间（仍 ≥30 候选），方案 B 略优（+4.2fps）——方案 A 的 simulateTarget 跨 1 万元素重算 + editBox 维护成本显现。
3. **瓶颈定位**：`editor.move` 单次同步成本 = n≤1k 时 8–10ms，n=10k 时 20.3ms（per-frame 移动 N 元素 + emit），是 10k 选区 fps 回落的主因（非覆盖物渲染本身）。
4. **逐梯度内存**：整体 final 102.8 MB（含 10 万图元 + 选区 + benchmark 副产物）远低于运行态 320 MB 红线；逐梯度 usedJSHeapMB 增量受 GC 噪声显著（实测出现负增量，无额外信息量），故不单列——内存非编辑态包络瓶颈，选区规模对内存的边际影响可忽略（10 万图元基体本身占主导）。

### 3.6 覆盖物挂载形态建议

## 选型路径建议（不裁定，仅供 E1.1 参考）

基于 E0.1+E0.2+E0.3 三项实测结论：**路径 A（leafer-editor 插件底座 + 自研组态语义适配层）成立**——主路径否决条件（手势仲裁不成立 / 事件族漂移成本≥自研成本）均不触发，编辑态性能候选达标（R7 包络数字待 E1.2 确立，不影响选型主路径）。建议 E1.1 选型 gate 采纳主路径 A。关键设计约束（输入 E2.1 编辑器架构）：

1. 图元必须显式 `editable: true`（双态切换：编辑态开 / 运行态关，双态隔离 R5 落点）
2. 选中触发必须真实点击（不能用 `editor.select()` API 替代完整接管——spike-mock-leak 教训）
3. 拖拽事件经 `editor.move` 派发（载荷 `{moveX, moveY, target}`），需在适配层监听 → 抽纯 payload + nodeId → `createNormalizedActionEvent`（**不能直传 leafer 事件**：携带循环 Leaf 引用）→ 转 diff（E2.4 undo-redo 设计落点，transform 事件族需节流起止帧）

5. scale 默认 `editSize:'size'` 改写 width/height（非 scaleX）；rotate 经 `rotateGap:45` 吸附；skew 触发 = ctrl+resize-line
6. 框选 selectArea：move:'auto' 冲突 + 默认 release 清空选区（E0.2 §2.3 新发现）——E2 设计需 `selectKeep:true` 或自定义 release，或双态切换 move 配置
7. group/ungroup 需适配层转组态模型结构 diff（addSymbol/removeSymbol，非属性增量）
8. InnerEditor 事件依赖 inner-editor 插件装载（`@leafer-in/text-editor` 注册 TextEditor）——编辑器包需引入对应 inner-editor 插件
9. 编辑态覆盖物采用方案 A（leafer Editor 内置，10k 选区仍 32fps ≥30 候选；方案 B 自研挂 sky 作 fallback 路径 B，性能可行）

## spike 局限性声明

- **scratch 单层 App vs runtime 3 层 App**：本 spike 为 `new App` 直接挂载，未跑 runtime 全量路径（registry/样式解析/组态构建/React 桥接）；E0.3 实例化 239ms 快于 runtime 373ms 基线即此差异体现（对齐 I1.2 spike 与 runtime benchmark-report.md §3.1 差异先例）。E1.2 编辑态包络确立时需在 runtime 3 层 App 下复测对照。
- **headless+swiftshader 下界**：所有 fps 数字为 Playwright headless Chromium `--use-gl=swiftshader`（软件渲染）测得，真实 GPU 浏览器数值更高——候选数字偏保守。内存经 `--enable-precise-memory-info`。
- **方案 A fps 测量口径**：editor.move 吞吐经内部 rAF 驱动 `editor.move()`（真实 TransformTool 代码路径，规避 page.mouse IPC 对 wall-clock 污染）；真实指针拖拽的端到端延迟（含命中检测 + simulateTarget 初始化）未单独测（per-call 同步成本 8–20ms 已证远低于 100ms 候选）。
- **程序化 select vs 真实点击**：E0.1/E0.3 用 `editor.target=list` 程序化选区激活 simulateTarget（E0.3 性能用）；E0.1 已证真实交互需真实点击（spike-mock-leak 教训），E0.2 事件族载荷抽取用真实手势。
- **覆盖范围**：单选/多选/框选/InnerEditor/transform 全族已验证；运行态（editable 关闭）交互不属本 spike 范围（双态隔离 E2 设计落点）。
