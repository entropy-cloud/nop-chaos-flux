# P1 Findings (material — should fix)

## [P1-1] `clearAll()` silently leaves every conversation in storage → ghost rehydration on reload

_Justification: real contract break + incorrect behavior on a public API — the method name and its symmetry with `deleteConversation` promise "clear everything", but the implementation aborts/detaches in-memory state only and never propagates the clear to storage; the result is that "deleted" conversations reappear from storage on the next mount. Zero test coverage._

- **Where:** `packages/flux-renderers-ai/src/adapters/use-conversation.ts:362-373` (impl); `:56` (public interface); documented at `docs/components/flux-renderers-ai/engine.md:266`.
- **What:**
  ```ts
  function clearAll(): void {
    for (const [, engine] of engineCache.entries()) {
      if (engine.getState().isProcessing) void engine.abort();
    }
    for (const id of engineCache.keys()) detachEngine(id);
    engineCache.clear();
    setConversations([]);
    setActiveId(null);
    setActiveEngine(null);
    // ⚠ no storage interaction whatsoever
  }
  ```
  Contrast with `deleteConversation(id)` (`:339-343`), which **does** call `await storage?.deleteConversation?.(id)` (with `reportStorageError`). `clearAll` is the lone list-mutator that diverges from the persistence layer.
- **Why it matters:** A host that wires a "Clear all" / "Reset workspace" button to `clearAll()` observes the conversation list empty immediately — but on the next mount the bootstrap effect (`:210-231`) runs `storage.loadConversations()` and **rehydrates every conversation `clearAll` claimed to remove**. The user perceives data that "won't die". This is the precise inverse of the silent-drop family the prior P1-2 remediation fixed for `create`/`rename` (FP-4): there the bug was _swallowed save errors_; here it is _a missing delete path_.
- **Root cause:** Two compounding gaps.
  1. **Implementation:** `clearAll` was written memory-only and never received the storage-routing pass that `create`/`rename`/`delete` got.
  2. **Interface:** `ConversationStorageStrategy` (`storage/types.ts:9-15`) declares `deleteConversation?` but **no bulk clear** (`deleteAll`/`clear`). So even a conscientious implementer has no single call — they must loop `deleteConversation` per id (and tolerate each being optional).
- **Test gap (P0-grade evidence absence):** `rg -n "clearAll" packages/flux-renderers-ai/src -g '*.test.*'` → **0 hits**. `clearAll` has no test at all — not for the happy path, not for the storage contract, not for the abort-on-in-flight behaviour its body performs. `MockStorageCalls` (`use-conversation-test-helpers.ts:61-67`) even has a `deleteConversation` counter that no `clearAll` assertion reads.
- **Confidence:** certain (impl + interface + doc + zero-coverage all verified against live code).
- **Fix sketch:** loop `storage?.deleteConversation?.(id)` for each cleared id inside a `try/catch` → `reportStorageError({phase:'deleteConversation', ...})` (mirror `deleteConversation`'s pattern). If a host truly needs atomic bulk clear, add an optional `clearAll?()` to `ConversationStorageStrategy` and prefer it when present. Add a regression test asserting `mockStorage.calls.deleteConversation` increments once per conversation and that a re-mount does not rehydrate cleared conversations.
- **Not the multi-audit P1-1:** that is the `deleteConversation` post-await stale-closure race (single-conversation, activeId). This is `clearAll` (all-conversations, storage). Different method, different defect class.

## [P1-2] `switchConversation` eviction silently destroys message history when no `storage` is injected

_Justification: silent user-data loss on a supported, plausible configuration (multi-conversation in-memory chat with `storage` left optional). The documented eviction policy is unconditional — it never checks whether storage can rehydrate — so a round-trip switch (A→B→A) with no storage rebuilds an empty engine and the prior messages are gone. No test asserts message survival across a switch-back._

- **Where:** `packages/flux-renderers-ai/src/adapters/use-conversation.ts:289-323` (switch + eviction); design basis at `docs/components/flux-renderers-ai/engine.md:276`.
- **What:** The hook's eviction loop runs on **every** switch:
  ```ts
  // :318-323
  for (const [cachedId, cachedEngine] of engineCache.entries()) {
    if (cachedId === currentActiveId) continue;
    if (cachedEngine.getState().isProcessing) continue; // keep background streams
    detachEngine(cachedId);
    engineCache.delete(cachedId); // ⚠ engine + its in-memory messages discarded
  }
  ```
  The rebuild path only rehydrates when storage is present:
  ```ts
  // :289-306
  let engine = engineCache.get(id);
  if (!engine) {
    engine = buildEngineFor(id);          // ⚠ seeds from createEngineOptions.initialMessages (shared, usually [])
    engineCache.set(id, engine);
    if (storage) {                         // ⚠ skipped entirely when no storage
      const stored = await storage.loadMessages(id);
      ...
      engine.setMessages(stored);
    }
  }
  ```
  Trace (no storage): create A (send msgs) → create B → `switchConversation('B')` evicts A's engine (A not processing) → `switchConversation('A')` rebuilds an **empty** engine for A (no `loadMessages` to call). A's messages are gone. `engine.md:276` documents the eviction ("切走时清理非活跃非 processing 的 engine") but **never caveats the no-storage case**, and `storage` is declared optional (`UseConversationOptions.storage?`, with the no-storage branch seeding from `initialConversations` at `:110-115`). So no-storage is a first-class supported mode in which this policy silently loses data.
- **Why it matters:** A host building an ephemeral multi-conversation chat (no persistence — a legitimate choice the optionality explicitly invites) will lose user messages whenever the user flips between two conversations. It is not obvious: you have to know (a) eviction is unconditional, (b) rehydration is storage-gated, (c) both interact on switch-back. The `switchConversation` test even acknowledges the rebuild — `"the engine should be the same instance if not processing (re-created on demand after eviction)"` (`use-conversation-switch.test.ts:36-37`) — but **asserts only `activeConversationId`/engine identity, never that messages survive** (`rg messages.length use-conversation-switch.test.ts` → 0 hits). So the data loss is invisible to the suite.
- **Priority note (honest rating):** This is data-loss-adjacent and the rubric lists "data loss" under P0. I rate it **P1, not P0**, because (a) it is confined to the optional no-storage config, (b) no persistence promise is broken in the storage-backed primary path (storage rehydrates correctly — verified by `use-conversation-storage.test.ts:42-70`), and (c) the no-storage mode is reasonably interpretable as "ephemeral by design". If maintainers consider no-storage a first-class supported mode rather than a degraded one, this should be re-rated to **P0**.
- **Root cause:** The eviction policy ("bound memory") was designed assuming rehydration always follows; the rebuild path then made rehydration storage-conditional, but the eviction was never made storage-conditional to match. The two halves were not co-validated for the no-storage intersection.
- **Confidence:** certain (full A→B→A trace with no storage; coverage gap confirmed).
- **Fix sketch (either):**
  1. Make eviction storage-aware: when `!storage`, do **not** evict non-active idle engines (accept the memory cost — there is no rehydration to recover them), or snapshot their `getMessages()` into a side `Map` and re-seed via `engine.setMessages` on rebuild; **or**
  2. Keep eviction but, on no-storage rebuild, restore the snapshotted messages instead of `createEngineOptions.initialMessages`.
     Add a regression test: no-storage, create A, `engine.sendMessage`, switch to B, switch back to A, assert `engine.getMessages()` still contains the user/assistant messages.

## [P2-2] `ai-voice-input` emits a duplicate `no-result` error for one session (`onerror` + `onend`)

_Justification: a single failed/empty recognition session fires `onError({reason:'no-result'})` twice (once from `onerror`, once from `onend`), forcing hosts to dedup; reachable on a stable widget, non-blocking._

- **Where:** `packages/flux-renderers-ai/src/renderers/ai-voice-input.tsx:146-162`.
- **What:**
  ```ts
  recognition.onerror = (event) => {
    const reason = event.error;
    if (reason === 'not-allowed' || reason === 'service-not-allowed') {
      fireError('permission-denied');
    } else if (reason === 'no-speech') {
      fireError('no-result'); // ← first emission (no-speech)
    } else {
      fireError('no-result'); // ← first emission (any other error)
    }
  };
  recognition.onend = () => {
    setStatus('idle');
    if (!gotFinal) {
      fireError('no-result'); // ← second emission (onend always fires after onerror)
    }
  };
  ```
  Per the Web Speech spec, `onerror` is always followed by `onend`, so any `no-speech`/unknown error yields **two** `no-result` events. The existing `ai-voice-input.test.tsx` scripts a synthetic recognition and does not assert error-event count, so the double-fire is unobserved.
- **Why it matters:** Hosts rendering a "no speech detected" toast will flash it twice, or must add their own dedup. Low blast radius (non-fatal, informational event).
- **Confidence:** likely (spec-guaranteed `onerror`→`onend` ordering; no count assertion in the test).
- **Fix:** gate the `onend` `no-result` emission on `!gotFinal && !errorAlreadyFired` (track an `errored` flag set in `onerror`), or suppress the `onerror` `no-result` and let `onend` be the single source.

## [P2-3] `ai-citations` sanitize can DROP citation markers (silent content loss), beyond the double-encoding the multi-audit already filed

_Justification: a previously-unrecorded, more-severe consequence of the same `sanitizeHtml(rawText)` root the multi-audit's P1-2 covers — DOMPurify parses the raw text as HTML and discards content inside forbidden tags, so a `[N]` marker living inside a `<script>`/`<style>`-like span vanishes entirely (not just visually mangled). Recorded per the open-ended rule that a new impact of a known root is still a new finding; shares the P1-2 fix, so rated P2 to avoid inflating plan scope._

- **Where:** `packages/flux-renderers-ai/src/renderers/ai-citations.tsx:66-67` (`sanitizeHtml(rawText)` → `parseCitations(safeText)`).
- **What:** The sibling multi-audit P1-2 documents the **display** failure (`5 < 3` → `5 &lt; 3`, React re-escapes). A distinct failure mode it did not examine: `sanitizeHtml` runs DOMPurify with `USE_PROFILES:{html:true}`, which treats the raw assistant text as HTML and **strips forbidden elements together with their text content** (script/style are raw-text/CDATA elements — their content is not reparsed as children, it is dropped). So assistant output like `see <script>doThing()</script> and [1] for details` where the marker ends up inside a stripped span loses the `[1]` entirely — `parseCitations` never sees it and no citation card is rendered. This is content **loss**, not a rendering artifact.
- **Why it matters:** Probability is lower than the double-encoding (requires the marker to fall inside a forbidden-tag span), but the failure mode is strictly worse (silent data disappearance vs visible mangling). It is fully resolved by the multi-audit P1-2 recommended fix ("drop `sanitizeHtml` for the inline-citations text path — React text rendering already escapes safely"), so no additional remediation scope is needed; this entry exists so the fix's verification case covers content preservation, not only entity rendering.
- **Confidence:** likely (DOMPurify content-dropping for forbidden raw-text elements is documented behaviour; specific `[1]`-in-stripped-tag case not executed live, but follows directly from the sanitize-then-parse ordering).
- **Fix verification note:** when implementing the P1-2 fix, add a test feeding `<script>x[1]</script> plain [2]` and assert the `[1]` citation is preserved (today it would be dropped).

# Free-form assessment

**Top 1-3 directions worth attention:**

1. **The storage-optionality seam is under-validated.** Both P1s (and the multi-audit's `deleteConversation` P1-1) cluster in `useConversation` at the boundary between the in-memory model and the optional persistence layer. The hook supports `storage?` but every cross-cutting method (`clear`, `delete`, `switch`) was validated primarily against the storage-backed path; the no-storage and bulk-clear intersections leak. A single "exercise every `useConversation` method in BOTH storage and no-storage modes, asserting both memory and storage side-effects" test pass would have caught P1-1 and P1-2 together. This is the highest-leverage follow-up.

2. **`clearAll` is an orphan in the public API.** It is documented (`engine.md:266`), exposed in the return type, has abort/detach logic — yet has zero tests and an undefined relationship to persistence. Either it should be a first-class citizen (storage clear + tests) or it should be deprecated/removed if hosts are expected to loop `deleteConversation` themselves. Its current half-built state is the kind of "looks done, isn't" surface that erodes trust in the hook contract.

3. **Debug-scaffold hygiene is slipping through the gate.** The two `tmp-sanitize-check.*` files (P2-1) survived a `pnpm check` / `pnpm lint` / `pnpm test` gate that the multi-audit reported as all-green and "442 passing". `scripts/verify-no-src-artifacts.mjs` catches `.js`/`.d.ts` build artifacts but not `.mjs` debug scripts or no-op `.test.ts` files. A cheap guard ("no file under `src/` may match `/^tmp-/`, and no `it()` body may be a bare tautology") would prevent recurrence.
