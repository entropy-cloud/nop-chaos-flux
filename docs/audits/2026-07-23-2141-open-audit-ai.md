## 详细发现（高价值项）

### F1.1 [P1/确定] 引擎无回合串行化，`sendMessage`/`send` 可重入

**位置**: `src/engine/create-engine.ts` `sendMessage:148`、`send:161`、`runTurn:169`；对照 `clear:522`、`setMessages:128`、`regenerate:543` 都有 `isProcessing` 守卫。

**问题**: `sendMessage`/`send` → `runTurn` 入口**无 `isProcessing` 守卫**。`clear`/`setMessages`/`regenerate` 都显式拒绝“流进行中”的调用，唯独两个发送方法没有。

**后果**: 回合进行中再次 `sendMessage`（入口：`ai:send` action `ai-action-provider.ts:74`、`component:sendMessage` `ai-component-handle.ts:54`、或 host 直调）会：① `createAbortController()` 覆写 `draft.abortController`（`create-engine.ts:188`），旧 controller 从 state 丢失 → 旧流无法 abort（孤儿）；② 两条流交错向同一 `messages` 追加/提交 assistant 占位，会话顺序/内容损坏；③ `requestState` 被互相改写。

**为什么值得关心**: `ai-sender.tsx:98` 的 `disabled={loading||...}` 只挡 UI 直发；`ai:send`/`component:sendMessage`/host 直调三条公共 API 都不串行。引擎是**公开导出的 host utility**，契约不应假设调用方先禁用按钮。这是会话数据完整性缺陷。`engine.test.ts` 无任何并发/重入用例。

**根因**: 设计假设“UI 串行”，但 engine/action/component 三层都未把串行内化；`clear`/`setMessages`/`regenerate` 有守卫说明作者知道 in-flight 风险，唯独漏 send。

**建议**: `runTurn` 入口加 `if (isProcessing) return/throw`（或 abort 后重发）；或维护单飞 promise。补一条“双发并发”回归测试。

---

### F1.2 [P1/确定] `useConversation.buildEngine` 静默丢弃 tool 配置

**位置**: `src/adapters/use-conversation.ts:83-93`；类型 `createEngineOptions: Omit<UseMessageOptions,'connector'>`（`:18`）含 `tools`/`toolExecutor`/`maxToolRounds`。

**问题**: `buildEngine` 只转发 `plugins`/`initialMessages`/`extraRequestParams`/`systemPrompt`/`adapter`，**遗漏** `tools`/`toolExecutor`/`maxToolRounds`（同包 `use-message.ts:63-75` 正确转发了这三项）。

**后果**: 用 `useConversation`（多会话/持久化）做 agentic tool-loop 的 host，每个会话引擎**无 tools、无 executor**。引擎 `create-engine.ts:232` 遇 `finish_reason:'tool_calls'` 即因 `!toolExecutor` 转 `error`（`tool-no-executor`）。P2 agentic 能力在 useConversation 路径下**永远不可用**，且无告警。`use-conversation.test.ts` 对这三项**零引用**。

**建议**: `buildEngine` 补齐 `tools`/`toolExecutor`/`maxToolRounds` 转发；补回归测试。

---

### F2.1 [P1/确定] `ai-voice-input` 无法停止识别 + 卸载不清理（隐私 + 泄漏）

**位置**: `src/renderers/ai-voice-input.tsx:86-147`。

**问题**: ① `handleStart` 里 `const recognition = new Ctor()`（`:93`）**未存进任何 ref**，仅活在闭包；② “再次点击停止” `handleClick:141-145` 只 `setStatus('idle')`，注释称 “Stop is handled by recognition.onend”，但 `setStatus` **不触发 `recognition.stop()`**——UI 显示已停、`SpeechRecognition` 仍在跑、麦克风仍开、回调仍触发；③ 无 unmount cleanup effect 调 `stop()`/`abort()`。

**后果**: 隐私（用户以为关了录音，麦克风持续采集至浏览器超时）；资源泄漏（recognition↔闭包互引用无法回收）；卸载后仍触发 host `onResult`/`onError`（stale props / 已卸载组件 setState）。

**建议**: `useRef` 持有 recognition；停止分支调 `recognitionRef.current?.stop()`；加 `useEffect(()=>()=>{ recognitionRef.current?.abort() },[])`。

### F1.3 [P2/很可能] `MessageStateAdapter` 接口是假抽象

**位置**: `src/engine/create-engine.ts:108,131,505,509,526,544`（6 处 `(adapter as unknown as { state: InternalMessageState }).state.*`）；接口 `src/engine/types.ts:217-224`；基类 `src/engine/state-adapter.ts:19-27`。

**问题**: `MessageStateAdapter.getState()` 只返回 `PublicMessageState`（无 `connector`/`abortController`），声称“解耦引擎与视图层”。但引擎实际需要这两个字段，用 `as unknown as {state}` 穿透接口读 `BaseMessageStateAdapter` 的 protected `state`。该字段只有两个内置子类（`BaseNativeAdapter`/`ReactMessageAdapter`）才有。

**后果**: 接口被作为公共扩展点导出（`index.ts` 导出 `MessageStateAdapter` 类型 + 两个工厂），暗示 host 可自定义 adapter。但**直接实现接口**（不继承基类，如 Zustand-backed）的 adapter 会让 `setConnector`/`clear`/`abort`/`abortController` 全部读到 `undefined` → `setConnector` 永远跳过、`abort` 永远 no-op、in-flight 守卫失效。`contract-honesty.test.ts` 只验 IO，未验 adapter 接口自足性。

**建议**: 要么把 `connector`/`abortController` 纳入接口（`getConnector()`/`getAbortController()`），要么把 adapter 降为非公开内部细节。当前“既导出又穿透”的中间态最差。

### F1.4 [P2/确定] `ai-message-list` 分组契约声明但未实现

**位置**: `src/renderers/ai-message-list.tsx:31,128`；`src/schemas.ts:98-101`；`src/ai-renderer-definitions.ts:82-85`。

**问题**: `groupStrategy`/`dividerRole`/`maxGroupSize` 在 schema 声明、在 definition 注册为 prop、renderer 还透传 `groupStrategy` 给 view——但 `AiMessageListView` **从不读取** `props.groupStrategy`，列表永远平铺。

**建议**: 实现分组，或先摘除三字段以免误导。

### F2.2 [P2/很可能] 卸载不 abort 在途流

**位置**: `src/adapters/use-conversation.ts:181-187`（unmount 只清订阅）；`src/adapters/use-message.ts`（无 unmount cleanup）。

**问题**: `useConversation` unmount effect 只取消 auto-save 订阅，**不 abort**；`clearAll:285` 会 abort 但卸载不触发 clearAll。`useMessage` 自建 engine 同样无卸载 abort。

**后果**: 路由切换/条件渲染卸载时，在途 engine 仍后台跑：`env.stream` 连接不释放、chunk 继续累积进无人订阅的 state、插件钩子继续执行。注意区分“switch-while-stream 背景保活”（有意，`:237-245`）与“整体卸载销毁”（应终止）——当前用同一套不清算逻辑混淆了两者。

**建议**: unmount effect 对**自建**（非外部注入）engine 调 `engine.abort()`；外部 engine 生命周期归 owner。

## 总评（最值得关注的 1-3 个方向）

1. **“全绿却藏雷”的测试盲区**——F1.1（回合重入）、F1.2（tool 配置丢弃）、F2.1（麦克风停不掉）三者在 typecheck/test/lint 全绿下共存，且都跨**公开 host-utility 契约**边界（engine / useConversation / 浏览器资源生命周期）。这指向：当前测试偏“happy-path + 契约静态校验”，缺少**并发、重入、卸载、配置透传**这类“跨边界连锁”用例。这是本包当前最该补的能力，比修单个 bug 更高 ROI。
2. **engine 是一个被低估的并发单元**——F1.1/F2.2/F2.3 共同表明：流式 engine 的“启动 / 取消 / 销毁 / 串行”四个语义没有被一致地建模。`clear`/`setMessages` 有 in-flight 守卫、`abort` 有空 mutate、connector 不查 signal、卸载不 abort——四处在“是否终止 / 谁负责终止”上各自为政。建议把 abort/turn-serialization/lifecycle 收敛进 engine 的单一职责（F1.1 修复时一并处理 F1.6/F2.3）。
3. **接口诚实度**——F1.3（假 adapter 抽象）+ F1.4（死契约）+ F1.5（错误信息丢失）+ F3.3（注释数量错）是一组“声明与实现不对齐”的主题。单独看都小，合起来说明包内“对外契约的真实性”尚未被系统校验（`contract-honesty.test.ts` 目前只盯 IO，可扩展到“接口方法是否被实现 / 转发参数是否完整 / 公共导出是否真自足”）。
