## #41 收口：wizard picker 真实点击主线程卡死根因修复（reaction 空 dependsOn fail-open 死循环）

### 落地内容

**问题**（docs/testing/2026/10-10.md #41，#40 的遗留）：form-wizard 步骤二部门 picker 按 #40 同款 v3 契约迁移后，**真实指针点击**触发器弹框"大概率不开"或主线程硬卡死 30s+（IAB 实测单次卡顿 gap 59s，标签页甚至崩溃到 chrome-error 页），合成 `el.click()` 时好时坏，无任何控制台报错。#40 时已隔离 dataStatePath/发布绑定/role 失焦等因素，怀疑方向为 wizard valuesPath × crud 挂载 × Base UI Dialog 时序。

**根因定位**（渲染器级，详见 docs/bugs/169）：无头 Chromium 复现后，`Profiler.stop` 会排在堵死的主线程后面永远取不到，改用 **CDP `Debugger.pause()`**（V8 中断在死循环中依然生效，即 DevTools 暂停按钮机制）连采 3 次现场栈，逐帧映射源码后闭环显形：

1. crud loadAction reaction 未声明 `dependsOn` → `createRootDependencySet` 返回 `undefined` → `scopeChangeHitsDependencies(change, undefined)` **恒 true**（fail-open）——对订阅链上任何 scope 变更都响应式重新 fetch；
2. `pickerSchema` region 无 slot 参数不建独立 fragment scope（`shouldUseFragmentScope = !!fragmentBindings`），弹框 crud 直接落在**表单 runtimeScope**，其自定义 `update` 把 `$_picker.rows`/`$_picker.selection` 写进**表单 values**（每次 fetch 都是新数组身份）；
3. 步骤表单 `valuesPath: wizardData.step2` 把 values 发布到 wizard scope（每次新对象身份，`Object.is` 守卫必然放行）；
4. `wizardData.step2` 变更沿组合 store 传播 → 不在 crud `ignoreWritesTo` 名单 → reaction 再 fetch → onSettle 再写 `$_picker.rows` → **无限 fetch/write/publish 循环**，叠加 React dev 模式全树 `warnUnknownProperties`/`logComponentRender` 吃满主线程。真实/合成点击只是进入循环的时序变量（fetch 与 force 的竞态决定能否自愈）——`ignoreWritesTo` 防的正是这类循环，但只盖 crud 自己拥有的路径。

**修复**（`flux-runtime/renderer-reaction-handle.ts`）：空 `dependsOn` 改 **fail-closed**——`handleScopeChange` 在无声明依赖时直接返回，不做任何反应式触发。编译器本就以 `invalid-reaction-deps`（error）要求声明 dependsOn，运行时对缺声明的正确姿态是"没有触发面"而非"监听一切"。命令式 `dispatch()`、显式 `force()`（刷新/reload）、crud 自身 state（分页/查询/排序）驱动的 load effect 重载均不受影响；已声明 dependsOn 的 reaction 行为不变。

**form-wizard.json 完成迁移**：#40 回滚的部门 picker 现按 standard-crud 同款 v3 契约迁移（valueField/labelField + pickerSchema crud region + `$_picker.*` 发布协议）；page-schemas 验证门禁基线同步收缩（`form-wizard.json` 的 `picker:loadAction/columns/valueKey/labelKey/searchable` 5 项删除，仅剩 `input-number:min` 声明缺口债）。
