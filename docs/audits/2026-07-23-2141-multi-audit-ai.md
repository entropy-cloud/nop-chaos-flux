### [AI-01] Engine `sendMessage`/`send`/`runTurn` lack concurrency guard (Bug 07 recurrence — duplicate concurrent turns)

- **Dimension**: 06 (Async patterns & cancellation safety)
- **File**: `packages/flux-renderers-ai/src/engine/create-engine.ts:148-189`
- **Evidence**:
  ```ts
  async function sendMessage(content: string | ChatMessageContentPart[]): Promise<void> {
    if (isEmptyContent(content)) return;
    const userMessage = adapter.createMessage({...});
    await runTurn([userMessage]);          // ← no isProcessing check
  }
  async function send(...messages: ChatMessage[]): Promise<void> {
    // ... no isProcessing check
    await runTurn(stamped);
  }
  async function runTurn(incomingMessages: ChatMessage[]): Promise<void> {
    const connector = adapterStateConnector();
    if (!connector) { /* error state */ return; }
    const abortController = createAbortController();
    adapter.mutate('requestState', (draft) => {
      draft.messages.push(...incomingMessages);
      draft.requestState = 'processing';
      draft.isProcessing = true;
      draft.abortController = abortController;   // overwrites any prior in-flight controller
    });
  ```
- **Severity**: P0
- **Current state**: Calling `sendMessage` twice (double-click before `isProcessing` propagates, two rapid `ai:send` namespace actions, or a `component:sendMessage` while a turn is in flight) starts two concurrent streaming turns; the second overwrites `draft.abortController`, orphaning the first controller so `engine.abort()` can never cancel it. Only `clear` (line 526), `setMessages` (line 131), and `regenerate` (line 544) guard `isProcessing`; the three primary send entry points do not.
- **Risk**: Duplicate LLM API calls (cost + side effects for tool-calling agents), interleaved `combineDeltaData` corruption of the shared assistant placeholder, permanently unstoppable background stream (orphaned AbortController = connection leak + ongoing token billing). The UI `disabled={loading}` button guard is bypassed by programmatic triggers (`ai:send` namespace, `component:sendMessage`, `user-edit.tsx` resubmit). This is the exact Bug 07 scenario at the engine tier.
- **Recommendation**: Add an entry guard mirroring Bug 07's fix: `if (adapterState.isProcessing) { return; }` (or abort the in-flight turn first). Return a canonical cancelled result so action chains treat it as ignored, not a business error.
- **False-positive exclusion**: NOT fail-safe (two overlapping turns corrupt shared state, not idempotent); NOT a two-arg `.then`; NOT a dynamic-import loader; NOT test/debug. The historical lesson explicitly calls out "all mutating async methods that have side effects should have a concurrency guard."
- **Historical pattern**: `docs/bugs/07-submit-concurrent-guard-fix.md` (root cause: `submit()` started without checking `submitting` state). The engine implements the guard for the _secondary_ methods but omitted it on the primary send path.
- **Doc reference**: `docs/bugs/07-submit-concurrent-guard-fix.md`; `docs/components/flux-renderers-ai/engine.md` §8.1.
- **Verification status**: Independently verified against `create-engine.ts:148-189` at HEAD.

### [AI-02] `engine.messages` live reference pushed into host scope (Decision-A / INV-17 violation)

- **Dimension**: 04 (State ownership & single source of truth)
- **File**: `packages/flux-renderers-ai/src/renderers/ai-chat.tsx:163-171`
- **Evidence**:
  ```ts
  const hostScopeData = useMemo(
    () => ({
      isProcessing,
      messages, // ← live engine-internal array reference
      activeConversationId,
    }),
    [isProcessing, messages, activeConversationId],
  );
  const hostScope = useHostScope(hostScopeData, props.path, 'ai');
  ```
  `messages` originates from `useEngineView` → `engine.getState().messages`, the domain-internal array. `useHostScope` → `HostScope.replace` writes the **same reference** into the scope snapshot without cloning.
- **Severity**: P1
- **Current state**: The renderer publishes the live engine messages array directly into the host scope, so descendants reading `${messages}` via `useScopeSelector` hold the engine's mutable internal array.
- **Risk**: Violates Decision-A (`design.md` §3 line 30: "host 必须 copy; 直接持有 engine 返回的引用会污染域内部"). A descendant or expression that mutates the projected array (or any nested message object) corrupts the engine's source of truth; streaming chunks then append onto a partially-mutated tree. Cross-package contract drift with `flux-runtime` host-projection which assumes projections are values, not live mutable internal state.
- **Recommendation**: Deep-clone (`structuredClone(messages)`) before constructing `hostScopeData`, or restrict projection to primitives (`isProcessing`, `activeConversationId`, `messages.length`) and require hosts to call `component:getMessages` for the full snapshot (Decision-A path).
- **False-positive exclusion**: NOT a low-code dynamic boundary — `messages` is a concrete mutable domain array, not a schema/payload edge where `any`/`Record<string,unknown>` is by-design. NOT transitional: Decision-A is the explicit adjudication that forbids reference sharing.
- **Historical pattern**: Bug 06 (ArrayEditor/CheckboxGroup dual-state) — domain store reference leaking into a second consumer that may mutate it.
- **Doc reference**: `docs/components/flux-renderers-ai/design.md` §3 (Decision-A), §11.5, §18.3 INV-17; `docs/architecture/scope-ownership-and-isolation.md`.
- **Verification status**: Independently verified against `ai-chat.tsx:163-171` at HEAD.

### [AI-03] `engine.abort()` reaches a stale/orphaned controller when a second turn overwrote it

- **Dimension**: 06 (Async patterns & cancellation safety)
- **File**: `packages/flux-renderers-ai/src/engine/create-engine.ts:180-189` + `:508-520`
- **Evidence**:
  ```ts
  async function abort(): Promise<void> {
    const controller = (adapter as unknown as { state: InternalMessageState }).state
      .abortController;
    if (!controller) return;
    controller.abort();
    // ...
  }
  ```
  Each `runTurn` overwrites `draft.abortController` (line 188); only the latest turn's controller is reachable. Combined with AI-01, an orphaned earlier turn cannot be aborted.
- **Severity**: P1
- **Current state**: `abort()` only ever cancels the most-recently-started turn; an earlier in-flight turn (created by an unguarded concurrent send) keeps streaming and commits into state after abort returns.
- **Risk**: User clicks "Stop", UI shows idle, but a background stream keeps running and silently appends a message when it completes — stale-response/out-of-order commit. For tool-loop agents this also means orphaned tool executions.
- **Recommendation**: Either track all in-flight controllers in a `Set` and abort all on `abort()`, or (better) enforce the AI-01 single-flight guard so overlap is impossible.
- **False-positive exclusion**: Not an orchestrator boundary — `abort()` is the documented cancellation primitive (engine.md §8.1) and must be reliable.
- **Historical pattern**: "cancelled/disposed boolean migrated to AbortController" — the package adopted AbortController but did not close the multi-controller overlap hole.
- **Doc reference**: `docs/components/flux-renderers-ai/engine.md` §8.1; `docs/bugs/07-submit-concurrent-guard-fix.md`.
- **Verification status**: Verified against `create-engine.ts:508-520` at HEAD.

### [AI-04] `ai-voice-input` SpeechRecognition is never stopped/aborted on unmount or toggle-off (microphone leak)

### [AI-12] `ai-chat` request-state subscribe effect re-subscribes on every render and resets `prev` (drops transitions)

- **Dimension**: 07 (Lifecycle)
- **File**: `packages/flux-renderers-ai/src/renderers/ai-chat.tsx:176-195`
- **Evidence**:
  ```ts
  useEffect(() => {
    let prev: RequestState = engine.getState().requestState;
    const unsubscribe = engine.subscribe('requestState', (state) => {
      // fires onResponseComplete/onError/onAbort when prev==='processing' && current!=='processing'
      prev = current;
    });
    return unsubscribe;
  }, [engine, props.events]); // ← props.events is a fresh object per NodeRenderer render
  ```
- **Severity**: P2
- **Current state**: `props.events` is rebuilt by `NodeRenderer` on most renders, so the effect tears down and re-subscribes frequently; each resubscribe re-reads `engine.getState().requestState` as `prev`, and if a transition happened between unsubscribe and resubscribe it can be missed.
- **Risk**: Schema transition events (`onResponseComplete` etc.) can be dropped when a re-render lands exactly between a `processing→completed` transition and the next effect run. Also an efficiency cost (frequent subscribe/unsubscribe churn during streaming).
